# FE-BE 협의 항목 카탈로그 (dt-devspec §2.5 B 기준)

> dt-devspec §2.5 협의완전성 검증(B)의 **기준 카탈로그** — 신규 프로젝트·페이지·기능에서 FE/BE가 합의해야 할 범용 항목 모음. 모든 프로젝트가 동일 카탈로그를 SOT로 참조한다.
> B 검증은 14항목 전부 강제가 아니라 **프로젝트 관련 항목 ∩ 정의서(전역 규약/IF/DM) 미커버분**만 §3 큐로 올린다(과부하 방지). "정의서가 이미 같은 항목을 명문화했으면 미커버 아님"이 1차 규칙.

---

## ⭐ 최우선 합의 TOP 5

비어 있으면 거의 확정적으로 사고가 나는 5가지. 무엇보다 먼저 잠근다.

- [ ] **① nullable / 타입 계약** — 빈 값이 `null`인지 `""`인지 키 자체가 없는지, 필드 타입 확정
- [ ] **② 에러 응답 포맷** — 에러 코드 체계 + 필드별 validation 에러 구조
- [ ] **③ 멱등성(idempotency)** — 생성·결제·업로드 재시도/더블클릭 시 중복 방지 방식
- [ ] **④ trace / correlation ID** — FE 에러와 BE 로그를 연결하는 요청 추적 ID
- [ ] **⑤ 타입 자동생성** — OpenAPI를 SSOT로 두고 타입 생성(드리프트 제거)

---

## 1. API 계약 (분쟁의 대부분이 여기서 발생)

- [ ] 엔드포인트: URL · HTTP 메서드 · 리소스 네이밍 규칙
- [ ] 요청/응답 스키마: 필드명·타입·**nullable 여부**·중첩 구조
- [ ] ID 체계: number vs string/UUID (JS 64bit 정수 정밀도 손실 → 큰 ID는 string 권장)
- [ ] 날짜/시간: 포맷(ISO 8601 권장) · **타임존**(UTC 후 FE 변환?)
- [ ] 페이지네이션: offset/limit vs cursor · total count 포함 여부
- [ ] 정렬·필터·검색 파라미터: 쿼리스트링 규약 (예: `?sort=name,-createdAt`)
- [ ] 에러 응답 포맷: 코드 체계 · 메시지 위치 · 필드별 validation 에러
- [ ] 스펙 공유 수단: OpenAPI/Swagger가 단일 진실 공급원(SSOT)인지

## 2. 인증 / 인가

- [ ] 인증 방식: JWT / 세션 / OAuth, 토큰 저장 위치
- [ ] 만료·refresh 토큰 처리
- [ ] 권한(role) 체계 — 어떤 화면·버튼이 어떤 권한을 요구하는지 (FE: 숨김 vs 비활성)
- [ ] 401/403 발생 시 FE 동작 (로그인 리다이렉트 등)

## 3. 책임 분담 ("누가 처리하나")

- [ ] 검색·정렬·필터를 서버 사이드 vs 클라이언트 사이드
- [ ] validation 규칙 — 양쪽 다 하더라도 **규칙 값 동기화**
- [ ] 파생 데이터(합계·상태 라벨 등)를 서버가 줄지 FE가 계산할지
- [ ] 실시간성: polling / WebSocket / SSE 필요 여부

## 4. 파일 · 미디어

- [ ] 업로드 방식: 서버 경유 multipart vs **presigned URL 직접 업로드**
- [ ] 파일 크기·확장자 제한
- [ ] 진행률 / 청크 / 재개 업로드 지원 여부
- [ ] 다운로드: 공개 링크 vs 인증 필요, presigned 만료
- [ ] 썸네일·미리보기 생성 주체 (서버 변환 vs FE 렌더)

## 5. 에러 · 엣지케이스 · 상태

- [ ] 빈 상태 / 로딩 / 에러 상태에서 서버가 주는 데이터 형태
- [ ] **일괄 작업의 부분 실패** (전체 롤백? 성공분만? 결과 배열?)
- [ ] 삭제가 soft delete vs hard delete (휴지통/복구 여부)
- [ ] 동시 수정 충돌 처리 (버전 / 낙관적 락)

## 6. 협업 프로세스

- [ ] Contract-first: 스펙 확정 → mock(MSW 등)으로 FE/BE 병렬 개발
- [ ] dev / staging / prod 엔드포인트, CORS 설정
- [ ] 스펙 변경 공지 채널 · 버저닝 정책

## 7. HTTP 시맨틱 합의

- [ ] 상태 코드 규약: 생성=201, 빈 응답=204, **비즈니스 에러를 4xx vs 200+에러바디**
- [ ] 부분 성공(207 등) 표현, 리다이렉트 정책

## 8. 멱등성 · 중복 · 재시도

- [ ] 생성/결제/업로드에 **idempotency key** 지원 여부
- [ ] 서버 재시도 정책 · 타임아웃 후 "성공 여부 불명" 상태 처리

## 9. 성능 · 캐싱 · 네트워크

- [ ] 캐시 헤더(`ETag` / `Cache-Control`) · 304 활용
- [ ] 응답 크기 / 필드 선택(sparse fieldset) · gzip·brotli 압축
- [ ] N+1·대용량 목록 → 페이지네이션 / 지연 로딩 · rate limiting

## 10. 보안 세부

- [ ] CSRF / XSS 방어 책임, 입력 sanitize 위치
- [ ] 파일 업로드 악성파일 스캔 · content-type 검증 · 경로 traversal 방지
- [ ] 민감정보 마스킹·로그 비노출, 권한별로 같은 엔드포인트라도 다른 필드 노출

## 11. 관측성 · 디버깅 (FE-BE 핑퐁 방지)

- [ ] **요청 trace / correlation ID** → FE 에러 ↔ BE 로그 연결
- [ ] 에러 추적 도구(Sentry 등) 연동 · 공통 에러 코드 사전

## 12. 타입·스펙 자동화 & 계약 테스트

- [ ] OpenAPI SSOT → **타입 자동 생성**(openapi-typescript 등)
- [ ] contract test로 스펙 변경 시 FE 빌드가 깨지도록

## 13. 버저닝 · 하위호환 · 점진 배포

- [ ] API 버전 정책 · deprecated 필드 유예 기간
- [ ] **feature flag / 점진 롤아웃** — BE·FE 배포 시점 불일치 흡수
- [ ] DB 마이그레이션 ↔ API 변경 배포 순서

## 14. 그 외 자주 누락

- [ ] i18n / 로케일: 다국어 메시지 주체, 숫자·통화·날짜 로케일
- [ ] 환경 분리: 환경변수, CORS
- [ ] 정렬 디테일: null 위치, 대소문자, 한글 초성/정렬 안정성
- [ ] 조직/프로세스: API 변경 공지, 결정권(RACI), BE 준비 시점 ↔ FE 시작 시점 동기화
