# dt-explain 답변 골격 (SOT)

> 종류: **참조 문서(형식 계약)** · 소비처: `dt-explain` SKILL.md.
> 문제 설명 답변의 절 구성·근거 라벨·모드 판정을 한곳에서 정의한다.

## 근거 라벨 (전 절 공통)

원인·사실을 말하는 모든 문장에 라벨을 붙인다.

- `🟢 확인됨` — 코드·로그·티켓을 직접 봄. 반드시 출처(파일:라인, 티켓 키, 로그 위치)를 함께 적는다.
- `🟡 추정` — 정황상 유력하나 미확인. "~로 추정됩니다. 확인하려면 X를 보면 됩니다" 형태로 쓴다.

**철칙 (systematic-debugging 차용):**
1. **원인 절 없이 해결책 절을 쓰지 않는다.** 원인을 모르면 "원인 후보와 확인 방법"까지만 답한다.
2. **🟡를 확정 어투로 쓰지 않는다.** 추정을 "~때문입니다"로 단정하는 순간 독자는 검증을 건너뛴다.

## 풀 모드 — 6절 고정 순서

### 1. 무엇이 문제인가
증상 / 언제(조건) / 어디서(컴포넌트) / 영향 — 각 한 줄. (5-Whys 문제 정의 템플릿)

### 2. 왜 생겼나 (원인 사슬)
"증상 → 왜? → … → 근본 원인"을 근거 라벨과 함께 잇는다.
- 각 고리마다 라벨 + 출처.
- **역방향 검증**: "근본 원인을 고치면 위 고리들이 사라지는가"를 스스로 점검하고, 안 사라지는 고리가 있으면 사슬을 다시 판다.
- 서술은 비난 없이 — "누가 잘못했나"가 아니라 "어떤 조건이 이걸 허용했나".

### 3. 쉽게 말하면 (예시)
구체 예시 1개 필수. **기본은 해당 프로젝트의 실사례** — 실제 화면·데이터·시나리오로 증상을 재현해 보인다
(예: "Alice가 댓글을 달면 목록엔 보이는데 '댓글 N개' 숫자는 그대로인 상황").
개념이 낯설어 실사례만으로 부족할 때만 일상 비유를 **보조로 추가**한다
(예: "편의점 재고표(캐시)가 새로고침(무효화) 전까지 예전 숫자를 보여주는 것").
비유를 쓸 땐 등장물 ↔ 시스템 구성요소가 **1:1** 로 대응돼야 한다 — 대응 안 되는 장식용 비유 금지.

### 4. 해결 방법 (2~3개)
방법마다 고정 4행. 추천안을 첫 번째로 두고 "(추천)" 표기.
- 어떻게: 무엇을 바꾸나 (파일·구성요소 수준)
- 왜 해결되나: 근본 원인의 어느 고리를 끊나
- 단점·주의점: 비용, 부작용, 새로 생기는 위험
- 이런 상황이면: 이 방법을 선택할 조건

### 5. 더 나은 제안 (선택)
선택지들 밖의 구조적 개선(재발 방지, 상위 설계)이 보이면 한 단락. 없으면 절 자체를 생략.

### 6. 한 줄 요약
비개발자에게 그대로 전달 가능한 한 문장 (기술 용어 없이).

## 퀵 모드

**조건**: 원인이 자명하고(🟢 라벨의 원인 고리 1개 이내) 현실적 해결책이 사실상 하나일 때.
**형식**: 첫 줄에 `(퀵 모드 — 원인이 단순해 축약함)` 명시 → 문제 한 줄 → 원인(라벨+출처) →
추천 해결책 1개 + 주의점 → 한 줄 요약. 예시 절은 원인이 개념적으로 어려울 때만 넣는다.

## 출력 전 게이트 (출력 전 점검 — 어기면 고친 뒤 출력)

- [ ] (readable-writing A1) 약어가 첫 등장에서 풀렸는가
- [ ] (readable-writing A2) 내부 용어·파일명에 한 줄 설명이 붙었는가
- [ ] (readable-writing B2) 주어가 분명하고 능동태인가
- [ ] (readable-writing B4) 한 문장이 한 개념인가
- [ ] (readable-writing C1) 앱·시스템·화면이 "알려 주다·기억하다·판단하다" 같은 사람 행위를 하지 않는가
- [ ] (readable-writing C2) `~에 의해`·`~을 통해`·이중 피동·`~중 하나`·직역 대명사가 없는가
- [ ] (readable-writing C3) `수행·존재·해당·요구되다` 같은 낯선 말이 일상어로 바뀌었는가
- [ ] (readable-writing C4) "결론적으로" 같은 상투 도입구·문두 접속사 반복이 없는가
- [ ] 위 항목은 `ko-writing-reviewer` 1회 리뷰로 확인했는가(미가용이면 lint + 직접 대조)
- [ ] (풀 모드) 구체 예시가 1개 이상인가 — 프로젝트 실사례 우선, 비유는 1:1 대응
- [ ] 원인·사실 문장 전부에 🟢/🟡 라벨이 있는가
- [ ] 해결 방법마다 "단점·주의점" 행이 있는가
- [ ] (퀵 모드) 축약 사실이 첫 줄에 명시됐는가
