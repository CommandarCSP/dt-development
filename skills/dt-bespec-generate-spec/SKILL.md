# dt-bespec Generate Spec (Backend SDD orchestrator)

리소스(REST noun, 예: `orders`)에 대한 백엔드 명세 4종을 다중 소스에서 생성하는 오케스트레이터.
출력: `docs/specs/resources/<resource-kebab>/`.

> FE의 `dt-spec-generate-spec`을 백엔드 맥락으로 미러링. 헤더/버전/머지 알고리즘 개념을 재사용한다.

## 입력 소스
- **OpenAPI/Swagger** (`.yaml`/`.json`) — 1차 계약 소스 (FE의 Figma 대응) → `dt-bespec-analyze-openapi`
- **ERD / SQL DDL / 데이터 모델 문서** → `dt-bespec-analyze-datamodel`
- **Markdown / PDF / Web** 요구사항 → `dt-bespec-analyze-document`

## 실행 모드 (컨텍스트 경제 — 격리 워커 + needsDecision HITL)

이 스킬은 **얇은 조율자**다. 무거운 작업(소스 분석·머지·빌드)은 일회성 워커 `bespec-author`(agents/)가 자기 컨텍스트에서 끝내고 포인터+요약만 돌려주게 한다. 모드는 `../../docs/orchestration-policy.md` 원칙 1·4를 따른다(FE `dt-spec`과 대칭).

- **dispatched (기본):** 조율자가 **§0 게이트만** 직접 수행 → `Task`로 `bespec-author` dispatch(`{ resources, sources, args, gateResult }`) → 워커는 아래 절차를 따르되 사람 결정은 `needsDecision`으로 반환·`.dt-spec/<resource>/`에 영속화 → 조율자가 `{ units[], interactions, needsDecision[], writingLint, summary }`만 받아 needsDecision 있으면 AskUserQuestion 후 재dispatch, 없으면 완료. 완료 보고의 summary 끝에 `한글 lint: 고침 N·유지 M`(writingLint)을 한 줄로 보인다. **여러 리소스면 리소스별 병렬 dispatch하지 말고 `resources` 목록을 한 bespec-author에 넘겨 홀리스틱하게** 짓게 한다 — 크로스리소스(트랜잭션 경계·cascade·스키마 머지 순서)를 한 시야에서 잡고 `interactions.md`의 BE 섹션을 산출한다.
- **inline degrade (원칙 4):** 조율자가 아래 흐름을 직접 수행(현행). 워커를 안 거칠 뿐 같은 절차·같은 산출.

> 두 모드는 아래 동일 흐름을 따른다(분기 없음). `bespec-author` 정의는 `${CLAUDE_PLUGIN_ROOT}/agents/bespec-author.md`.

## 흐름

0. **개발 정의서 게이트 (소프트)** — **먼저 스코프를 해소**(아래 "§0-스코프 해소")한 뒤 `scripts/checkDefinitionGate.mjs`를 `{ projectRoot, scope }`로 호출해 판정(`kind`)을 받고 분기한다(FE `dt-spec-generate-spec`과 대칭; scope 미해소면 `scope` 생략 = bare `definition.md`). **게이트는 판정만, 수락/거절 결정은 여기서 사용자에게 묻는다.** 자동으로 다른 스킬을 호출하지 않는다 — 사용자가 다음 스킬을 직접 실행한다.

   **§0-스코프 해소 (다중 스코프 — 어느 정의서를 소비?):** `parseDefinitionSources.discoverDefinitions({ projectRoot })`로 `definition*.md`를 발견한 뒤 다음 **우선순위**로 해소(먼저 맞으면 종료): ① **`--scope <slug>` (최우선)** — 헤더와 달라도 이긴다(잘못 바인딩 교정), 적용 후 leaf 헤더 갱신 → ② **헤더 scope**(`<!-- scope: <slug> -->`) → ③ **레거시 면제** — scope·`--scope` 없고 `<!-- basedOnDefinition: N -->`만 있으면 bare `definition.md`, **질문 안 함** → ④ **단일** — `definition*.md`가 1개면 그걸 사용 → ⑤ **다중·미지정** — `AskUserQuestion` **1회 질문**(자동 추정 금지), 답을 `buildSpecHeader`의 `scope` 필드로 leaf 헤더에 기록.
   - **`consume`**: 정의서 소비. `authorKind:'generated'`면 IF 3분기(`확정`=lock / `미해소`=스펙화 스킵 / 그 외=보강); `authorKind:'hand-authored'`면 값 전부 잠정(아래 IF 합의상태 재확인 시드로만). `migrate:'in-memory'`면 읽기 전용 흡수(정의서 직접 수정 금지). `status:'draft'`면 "미해소 N건, 계속?" 확인 + **미해소 IF 스펙화 스킵 + 참조 SP/엔드포인트 자리에 `<!-- skipped: IF-n (미해소) -->` 마커 emit**. consume일 때 `definitionVersion`+`definitionPath`(leaf→정의서 상대경로)+`definitionIfIds`(이 리소스가 참조한 IF)를 step 6 `buildSpecHeader`로 넘겨 **신규격** `<!-- basedOnDefinition: <상대경로>@v<N> | IF-a,IF-b -->` emit(dt-devspec 「마커 규격」 절 참조) — **이 줄이 Task 6 쓰기측 규약이자 `extractBasedOnDefinition`(변경 전파)의 입력**이다(손 주석 주입 금지). BE는 본문 `<!-- from: IF-n -->`도 심으므로 `computeImpacted`가 from-refs+IF 리스트를 합산한다.
   - **`none`**(정의서 없음): "최소 정의서 만들까요?" **수락**이면 **헤더 없는(hand-authored) 골격 스텁**(추론 IF/SP 전부 `협의중`) 작성 + `/dt-devspec` 안내 — *`Generated by dt-devspec` 마커를 leaf가 달지 않는다*(마커 사칭 금지; 다음 실행에서 hand-authored로 재진입). **거절**이면 standalone(`buildSpecHeader`에 `definitionSOT:'none'`).
   - **`needsNormalization`**(대충 손작성): "`/dt-devspec`으로 정규화할까요?" **수락**=산출물 없이 종료(사용자가 `/dt-devspec` 후 재실행). **거절**=standalone(`definitionSOT:'unstructured'`) **+ 대충 정의서 상단에 `<!-- NOT-SOT: unstructured, used as hint by dt-bespec/<resource> -->` 비파괴 주석을 diff-then-confirm으로 1줄 추가**(idempotent — 이미 있으면 skip; 나중 `/dt-devspec` D12 정규화 복구의 단서이자 거절 재감지 신호).
   - **`corrupt`**: "정의서 깨짐 — `/dt-devspec` 재생성" 안내 후 미산출 종료(standalone 강등 금지).
   - **`versionTooHigh`**: "플러그인 업그레이드 필요" 안내 후 미산출 종료.
   - 엔드포인트/스키마를 *추론*하기 전, 정의서 **IF-n을 합의 상태에 따라** 사용한다:
     - **확정(agreed) IF** → lock. 그대로 인용한다. 재추론·임의 변경 금지.
     - **협의중(tentative) IF** → 잠정 계약이므로 leaf가 deep-read로 **보강·구체화 가능**. 보강 결과는 아래 "## 상향 정합"으로 정의서에 환류한다.
   - 자기 담당(**BE/공통**) SP/IF만 스펙화하고 **FE 전용 항목은 스킵**한다.

#### §0-b. 입력 소스 ∩ 어댑터 교차 (G1/G2)

입력 소스 타입 ∩ 이 스킬 어댑터(OpenAPI/ERD/문서)를 교차한다(dt-bespec엔 Figma 어댑터 없음).
- **공집합**(예: Figma뿐): `none+수락`이라도 스텁이 빈 껍데기 → **스텁 생략·미산출 종료** + "이 입력(UX)은 BE가 직접 못 읽습니다 — `/dt-devspec`을 먼저" 라우팅.
- **부분집합**(예: Figma+OpenAPI): 읽히는 소스로 진행하되 못 읽는 IF-bearing 소스를 소스 단위 적시 + `<!-- partial: Figma-only IF 미수거, /dt-devspec 선행 필요 -->` 마커 emit + "일관성 미보증" 경고. 거부·강행 시 그대로 진행(소프트).

1. **소스 해석**: locator 파싱 + 타입 감지(.yaml/.json→openapi, .sql/erd→datamodel, .md/.pdf/url→document) → 콘텐츠 로드.
2. **프로젝트 컨텍스트 수집/조회**: `dt-bespec-collect-project-context` → `docs/project-context.md` (framework/orm/db/auth/규약).
> 실행 모드는 `../../docs/orchestration-policy.md` 원칙 1을 따른다 — 소스 2개 이상이면 시작 시 병렬/순차를 1회 확인(기본 병렬). 순차 선택 시 어댑터를 직렬 서브에이전트로 분석.

3. **소스별 어댑터 분석**(병렬): 각 어댑터가 partial ExtractionResult 반환 (endpoints, schemas, dataModel, requirements, businessRules).
4. **2단계 머지**: (a) 구조 머지(endpoint 키 기준 union/null-completion/conflict) + (b) 정합 패스 → `_conflicts` / `_possibleDuplicates`.
5. **해소 + 보완**: `dt-bespec-ask-missing` → 충돌 해소 + 누락 method/endpoint/schema/status/authz를 EARS 질문으로 채움.
6. **산출물 작성**: `templates-backend/*.tmpl`을 채워 4개 파일 생성/갱신. 헤더는 `scripts/buildSpecHeader.mjs` 재사용(brand `dt-spec`) — **§0이 `consume`이면 `definitionVersion`+`definitionPath`+`definitionIfIds`를, standalone이면 `definitionSOT`를 `buildSpecHeader({ generatedAt, status, sources, definitionVersion, definitionPath, definitionIfIds })`로 전달**하면(consume 시) 헤더에 신규격 `<!-- basedOnDefinition: <상대경로>@v<N> | IF 리스트 -->`가 emit된다(`definitionPropagation.extractBasedOnDefinition`의 입력, 변경 전파용; `definitionPath` 없이 `definitionVersion`만 주면 구 정수형 하위호환).
   - **역참조 emit (변경 전파 입력)**: 정의서 항목을 스펙화할 때 출처 역참조를 써넣는다 — `requirements.md`의 각 EARS 요구사항 옆에 `<!-- from: SP-n -->`/`<!-- from: IF-n -->`, `api-contract.md`의 각 엔드포인트 행에 `<!-- from: IF-n -->`. 이 역참조가 `definitionPropagation.computeImpacted`의 입력이 되어, 정의서 변경 시 영향받는 요구사항/엔드포인트를 정밀 산출한다. emit하지 않으면 변경 전파가 작동하지 않는다.

## 변경 전파 (정의서 버전 비교) — FE와 대칭

**§0이 `consume`을 반환했을 때만 이 절이 적용된다**(standalone=`definitionSOT`이면 비교 기준 정의서가 없어 변경 전파/isStale 전체 비적용). consume일 때:
1. §0 게이트가 반환한 `definitionVersion`(= currentVersion) 사용.
2. 기존 산출물 헤더의 `extractBasedOnDefinition()`(= basedOnDefinition) 획득.
3. `isStale(basedOnDefinition, currentVersion)`가 true면 "영향받는 요구사항/엔드포인트 재검토 필요" 경고.
4. `computeImpacted(changedIds, specMarkdown)`로 정의서에서 바뀐 SP/IF 중 이 spec이 `<!-- from -->`로 참조하는 것만 정밀 나열. **자동 재작성은 하지 않는다**(diff-then-confirm으로 사용자 확인 후 갱신). 갱신 시 `definitionVersion`+1 + `<!-- updatedBy: dt-bespec/<resource>@vN -->` provenance + 자기 스펙 `basedOnDefinition`도 동시 갱신(self-stale 회피). **변경 전파와 상향 정합은 별개 쓰기 계기 — 한 실행에서 버전 이중 bump 금지.**

## 상향 정합 (deep-read ↔ 정의서 IF diff) — 게이트 + 쓰기 (T2~T8)

산출 직전, deep-read로 얻은 실제 계약을 정의서 IF와 diff하고 잠정 IF를 승격한다. 전체 절차(T2~T8·D8·H3·compare-and-swap·쓰기 순서)는 `${CLAUDE_PLUGIN_ROOT}/docs/refs/upward-alignment.md`를 Read해 적용한다 — **이 스킬은 BE이므로 `deepRead`=OpenAPI/데이터모델 추출 계약, `unitRef`=`dt-bespec/<resource>`. Figma 출처 IF의 T7 재추론은 비적용(G1 한계)**. §0이 `consume`(generated)일 때만 적용.

## 최종 정합 게이트 (산출 **후** — SOT 반영 강제, 필수)

**step 6(산출물 작성) 후, 상태를 finalized로 확정하기 직전에 반드시 실행한다.** 산출 과정(ask-missing·소스 우선순위·3-way)에서 최종 `api-contract.md`가 SOT와 벌어질 수 있으므로, **최종 api-contract 계약을 정의서 IF와 다시 diff**해 강제 정합한다. 절차·강제 규칙은 `${CLAUDE_PLUGIN_ROOT}/docs/refs/upward-alignment.md`의 **"최종 정합 게이트 (산출 후 — SOT 반영 강제)"** 섹션을 그대로 적용한다:
- diff의 **대조 차원**(응답 shape 필드·정렬/페이지네이션 규약·상태코드 + contract-elements 준용)은 `upward-alignment.md` §대조 차원을 따른다 — IF 행 존재만 보지 말 것.
- 최종 api-contract ↔ SOT IF 드리프트가 있으면 **반영(정의서 갱신 T2/T3, `확정`은 재확인/§3 큐) 또는 명시적 큐잉** 중 하나를 **강제** — 조용한 드리프트 금지.
- **미반영 드리프트가 0일 때만 `status: finalized`**. 하나라도 남으면 `status: draft`. (consume일 때만; standalone은 SOT 없음 → 비적용.)
- 변경 전파·산출 직전 상향정합과 **버전 이중 bump 금지**(같은 실행이면 그 위에서 재diff).

## 소스 우선순위 (다중 소스 충돌 해소) — [7-0]
2단계 머지의 `_conflicts`는 "어느 소스가 옳은가"를 **차원별 권위**로 해소한다 — 단일 글로벌 랭크가 아니다. `dt-bespec-ask-missing` Step 0이 이 사다리로 자동 해소(또는 기본 선택)하고, 모호할 때만 묻는다.

| 결정 차원 | 권위 순위(높음→낮음) | 근거 |
|---|---|---|
| 와이어 포맷(필드명·shape·status) | ① 런타임 계약/OpenAPI → ② ERD → ③ 산문 문서 | 돌아가는 계약이 곧 상호운용 진실 |
| 데이터 타입·제약 | ① ERD/SQL DDL → ② OpenAPI → ③ 문서 | DB가 타입의 진실 |
| 비즈니스 규칙(무엇이 일어나야) | ① 요구사항 문서 → ② 나머지 | 의도는 산문이 담음 |

- **런타임 계약 = 1급 소스**: 이미 동작하는 클라이언트가 기대하는 와이어 포맷(기존 FE의 mock 핸들러·타입·실호출 캡처, 배포된 OpenAPI)은 필드명/shape에서 **산문 문서를 이긴다**. 예: 문서가 `authorId`라도 FE 계약이 `userId`면 `userId`로 확정(무수정 연동 보장).
- 차원이 갈리면 차원별 권위를 따른다(같은 충돌이라도 "필드명"은 런타임, "타입"은 ERD, "규칙"은 문서).
- 사다리로 해소된 항목은 `source: 'precedence-resolved'`. 권위 소스가 둘 다 침묵하거나 동급 충돌이면 사용자에게 질문.

## EARS 패턴 (백엔드 적응) — [7-1]

| 원천 | 패턴 | 키워드 |
|---|---|---|
| 요청 트리거(POST/PUT/DELETE 액션) | Event-driven(request) | `WHEN <client sends request> THE SYSTEM SHALL ...` |
| 항상 성립(모든 응답에 인증/페이지네이션) | Ubiquitous | `THE SYSTEM SHALL ...` |
| 인증/역할 상태 | State-driven | `WHILE <authenticated as admin> THE SYSTEM SHALL ...` |
| 기능 플래그/선택 기능 | Optional | `WHERE <feature enabled> THE SYSTEM SHALL ...` |
| 검증실패/FK충돌/4xx·5xx | Unwanted(error) | `IF <error condition> THEN THE SYSTEM SHALL <status/code>` |
| 다중 조건 | Complex | `WHEN ..., WHILE ... THE SYSTEM SHALL ...` |

> Unwanted(error)는 백엔드에서 가장 풍부 — HTTP 상태코드 + 에러 계약과 직결.

## 인덱스 & 페이지네이션 전략 도출 — [7-2]
산출물 작성 시 조회 패턴으로부터 인덱스/페이지네이션을 도출해 채운다.
- **design.md `{{INDEX_PAGINATION}}`** (리소스별): 각 조회 경로(`where`/`orderBy`/FK join)를 인덱스로 매핑하고, 목록 엔드포인트마다 cursor/offset/비페이지네이션을 근거와 함께 선택.
  - FK·조회 조건·정렬 컬럼 → 인덱스. 합성 유니크(`@@unique`)가 커버하는 조회(좋아요 존재/멱등 upsert 등)는 그 사실을 명시하고 별도 인덱스 생략.
  - 정렬과 결합되는 빈번한 조회는 복합 인덱스(`@@index([authorId, id])` 등) 후보로.
  - 무한 증가 목록(피드/댓글)은 cursor 페이지네이션 기본. 유한·소규모 목록(추천 N명, 내 팔로잉)은 비페이지네이션 허용 — 단 "대량화 시 cursor 도입" 단서를 남김.
- **project-context.md `{{PAGINATION}}` / `{{INDEXING}}`** (전역): 모든 리소스가 따르는 표준 형태. cursor 요청/응답 계약(`?cursor=&limit=` → `{ items, nextCursor }`)과 인덱싱 정책(FK/조회/정렬 컬럼 인덱스 원칙)을 한 곳에 고정. 리소스 design.md는 이 표준을 참조만 한다.

> projectContext.projectLibraries(전역 세트 외 채택 lib)가 있으면 design.md 아키텍처 절에 명시해 후속 scaffold/implement가 그 lib를 쓰도록 한다.

## 인증 발급 도출 — [7-3]
인증의 **발급(issue) 측**(register/login/refresh)을 다룬다. 검증(verify)만 가정하지 않는다.
- **소스-퍼스트**: 원천이 인증을 명시하면(OpenAPI `/auth/*`·security scheme, ERD `passwordHash`/refresh/role) 그대로 추출 — 캐논 레시피 주입 안 함.
- **트리거 fallback**: 원천이 발급에 침묵하면 `dt-bespec-ask-missing`의 "인증 발급 트리거"로 확인. Y → `templates-backend/auth-recipe.md`의 캐논 auth 리소스를 instantiate(`docs/specs/resources/auth/`), `User.passwordHash` + refresh 저장 모델 delta 포함. N → 외부 발급 가정(현 동작).
- **WHAT vs HOW**: 엔드포인트·토큰 종류·필드는 원천이 결정. NestJS 구현 패러다임(Passport + JWT)은 원천이 침묵하면 하우스 스타일이 채운다 → `dt-backend-architecture` 인증 절.
- 캐논 레시피는 인증의 "Case 2 기본값"이다. 자세한 형태는 `templates-backend/auth-recipe.md`.

## 토글/멱등 관계 도출 — [7-4]
좋아요·팔로우·북마크·구독처럼 **켜고/끄는 멱등 관계**는 매번 손으로 짜지 않고 캐논 레시피로 instantiate한다.
- **감지 신호**: M:N 액션 엔드포인트 `POST`/`DELETE` 쌍이 `204`(바디 없음)를 반환 + read 모델에 `<rel>Count`/`<rel>edByMe` 필드. `dt-bespec-ask-missing`의 "토글 트리거"로 확인.
- Y → `templates-backend/toggle-recipe.md` 캐논 instantiate: 조인 테이블(복합 PK `@@id([actorId, targetId])` + `@@index([targetId])`), `upsert`/`deleteMany` 멱등, 부모 응답에 `count`/`byMe` 집계 투영, actor=토큰 sub(바디 금지).
- **WHAT vs HOW**: 토글 endpoint·필드명은 원천이 결정. 멱등·집계·신원 패러다임은 레시피가 채운다. 자세한 형태는 `templates-backend/toggle-recipe.md`.
- 원천이 이미 토글 계약을 명시하면 그것을 우선(소스-퍼스트). 본 레시피는 "Case 2 기본값".

## api-contract.md 3-way 분기 (FE layout-skeleton 대응)
- **Case 1 — 정밀**: OpenAPI 소스 존재 → 엔드포인트/스키마 충실 추출, Prisma 스케치 동반.
- **Case 2 — 구조적**: 문서/데이터모델만 → 엔드포인트·Prisma 모델 *추론*, `[inferred]` 마커 + `status: draft`.
- **Case 3 — stub**: API/데이터 단서 없음 → stub 안내("OpenAPI 또는 데이터모델 문서를 추가하세요").
