# dt-worklog-sync 설명·댓글 템플릿 (단일 소스)

스킬은 이 템플릿의 `{슬롯}`을 커밋·세션·수동 메모에서 채워 트래커에 쓴다. 어느 절을 쓸지는 설정의 `templates`(프리셋)다 — `basic`은 TP-002(`docs/policies/TP-002-task-records.md`), `org-guideline`은 아래 마지막 절이다.

- 댓글은 `contentFormat: "markdown"`으로 쓴다. 아래 설명 템플릿은 읽기 좋게 markdown으로 적었지만, **완료 조건 체크박스가 있는 설명은 HTML task list로 바꿔 쓴다** — Jira의 markdown 변환은 `- [ ]`를 체크박스로 만들지 않는다(SKILL 흐름 5).
- 슬롯을 맥락에서 채울 수 없으면 지어내지 말고 `{확인 필요}`로 두고 dry-run에서 묻는다.
- `← 있을 때만` 줄은 값이 없으면 줄째 뺀다.
- 문장은 `${CLAUDE_PLUGIN_ROOT}/docs/refs/readable-writing.md`를 따른다 — 약어 첫 등장 풀어쓰기, 내부 용어 설명, 한 문장 한 개념.

## basic

### 설명 (이슈를 만들 때)

"어떻게"는 설명에 넣지 않는다. 진행 과정은 댓글로 남긴다.

```markdown
## 배경
{왜 하는가 — 문제나 요청. 요청이면 출처 한 줄}

## 목표
{무엇이 되면 끝인가 — 1~2문장}
- 범위 밖: {이번에 하지 않는 것}   ← 있을 때만

## 완료 조건
- [ ] {확인할 수 있는 조건}

## 참고
- {스펙·디자인·관련 이슈·관련 문서 링크}
```

Bug는 "목표" 자리에 아래를 쓴다(나머지는 같다):

```markdown
## 재현
1. {재현 절차}

## 기대 · 실제
- 기대: {정상 동작}
- 실제: {결함 동작}
- 환경: {브라우저·OS·버전·데이터 조건}
```

### 진행 댓글 (작업 중, 상태를 바꿀 때)

```markdown
**진행** — {진행 중 | 막힘 | 검토 대기}
- 한 일: {이번에 한 것}
- 다음: {다음에 할 것}
- 막힌 것: {누구의 무엇이 필요한지}   ← 있을 때만
- 산출물: {PR·커밋·문서 링크}         ← 있을 때만
- 관련 문서: {문서 링크}              ← 있을 때만
```

### 마무리 댓글 (Done 직전, 반드시 하나)

```markdown
**완료**
- 결과: {무엇이 바뀌었나 — 1~2문장}
- 산출물: {PR/커밋, 문서, 배포 URL, 테스트 결과}   ← 산출물이나 결정 사항 중 하나는 꼭
- 결정 사항: {무엇을 왜 정했나, 버린 대안}          ← 오래 갈 결정이면 PD 문서 링크
- 완료 조건: {설명의 체크박스 n/n — 못 채운 것은 이유}
- 관련 문서: {문서 링크}                            ← 있을 때만
- 남은 일: {후속 이슈 키}                            ← 있을 때만
```

Done으로 넘기기 전에 `node "${CLAUDE_PLUGIN_ROOT}/scripts/worklogConfig.mjs" check-close <댓글 파일>`이 통과해야 한다(결과 + 산출물이나 결정 사항).

### 관련 문서 줄

이번 작업과 관련된 위키 문서(Confluence)가 이미 있으면 진행·마무리 댓글의 "관련 문서"에 넣는다. 형식은 `dt-confluence-doc`의 역링크(§7)와 같다:

- `📄 [{문서 제목}]({URL}) ({종류} · {작성일})`

여러 개면 `, `로 잇는다. 이슈에 이미 있는 링크는 다시 넣지 않는다.

## org-guideline

사내 가이드라인 프리셋의 템플릿이다(`presets/org-guideline.md`). 산출물 링크의 1차 위치는 산출물(Output) 커스텀 필드다 — 커밋/MR의 GitLab URL 자체를 그 필드에 멀티라인으로 기재한다. 아래 DoD 체크·댓글의 산출물 링크는 보조다. 관련 문서는 댓글 끝에 `📄 관련 문서: …` 줄로 붙인다.

### 설명 — 공용 (Sub-task / Story / Task)

```markdown
## 무엇을 (What)
{한 줄 요약 — summary와 중복 아닌, 작업 범위 1~2문장}

## 왜 (Why)
{배경·목적. 구두/메신저 요청이면 출처 한 줄(가이드라인 룰 6)}

## 어떻게 (How)
- {접근 방식 / 주요 변경점}
- {관련 파일·모듈}

## 완료 조건 (DoD)
- [ ] {검증 가능한 완료 기준}
- [ ] {산출물(커밋/MR/테스트결과) 첨부 — 룰 7}
```

### 설명 — Bug 변형

Bug는 How 자리에 재현·기대/실제 섹션을 끼운다. 나머지는 공용과 동일.

```markdown
## 무엇을 (What)
{결함 한 줄 요약}

## 왜 (Why)
{영향 범위·심각도}

## 재현 (Repro)
- {재현 절차}

## 기대 · 실제 (Expected / Actual)
- 기대: {정상 동작}
- 실제: {결함 동작}

## 완료 조건 (DoD)
- [ ] {수정 검증 기준}
- [ ] {산출물 첨부}
```

> Bug의 `Deployed→해결방법`, `Verified→검증방법`은 description이 아니라 아래 코멘트 템플릿으로 작성한다.

### 댓글 — 진행 업데이트 / 상태 전이 공통

```markdown
{진행 내용 자유 서술 — 무엇을 했고 다음은 무엇인지. 상태 전이 시 전이 사유를 첫 문장에}

**산출물**: {커밋/MR/테스트결과 링크}
```

규칙:
- 고정 헤딩 없음. 한 줄이든 문단이든 자유.
- 산출물 링크 줄은 권장 필수. 링크가 없으면 "링크 없이 진행만 기록할까요?"를 1회 확인.
- Bug `Deployed→해결방법` / `Verified→검증방법`, Sub-task `Done→산출물`도 이 같은 템플릿으로 작성.
