# dt-audit 협의 루프 (§4) — 카드 형식·결정 기록·라우팅

리포트 산출 후, 결정이 필요한 항목(SB 전건 + 🔴 + action=confirm)을 **하나씩** 협의한다.
순서: SB(스펙 보강) → 🔴(확인 필요) → confirm. dt-devspec §3 협의 패턴 준용
(기초→파생 순서·큐 완전소진). 워커는 사용자에게 직접 묻지 않는다 — 협의는 조율자 몫.

## 협의 카드 (항목당 1회 제시 → AskUserQuestion)

**카드는 AskUserQuestion 안에 임베드한다 (필수 — 도그푸딩 실측 결함 <!-- from: audit 2026-07-24-spec R1 -->).**
카드 설명을 본문 텍스트로 쓰고 질문만 툴로 띄우면 다이얼로그에 맥락이 안 보여 사용자가 판단할 수 없다.
- **question 필드** = 아래 1~4 요소의 자기완결 요약(다이얼로그만 보고 결정 가능해야 함)
- **각 option의 preview** = 그 선택이 만들 결과 초안(스펙 문구·코드 변경·마커)
- 관련 항목은 한 콜에 최대 4블록까지 군집화 가능(dt-devspec §3 규칙 준용) — 단 각 질문이 자기완결일 것.

1. **코드 현황** — 파일:라인 + 실제 동작을 평이한 말로 ("댓글이 오래된순으로 나옴")
2. **스펙 현황** — 어느 문서가 뭐라는지, 어긋난 지점
3. **왜 이렇게 됐나** — specDiagnosis 기반 원인 진단 (침묵/모호/모순/부재)
4. **일반적 처리 관례** — 업계 표준 + 같은 프로젝트 내 유사 결정(예: 피드는 BE 최신순).
   불확실하면 웹 리서치 1회 허용(상시화 금지 — 토큰 가드).
5. **추천 + 선택지** — 추천을 첫 옵션으로. 기본 선택지: 구현대로 승격 / 다르게 정정 / 보류.
