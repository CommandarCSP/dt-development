# 참조: FE 스펙 완성도 점검 체크리스트 (fe-spec-checklist)

> 종류: **참조 문서(성장형 체크리스트)** · 소비처: `dt-spec-generate-spec`, `spec-author`.
> 목적: FE 스펙 생성 시 **"개발에서 반드시 고려돼야 할 사항"** 을 한 곳에 체크리스트로 모아, 스펙과 대조해 **해당사항이 있는데 빠졌거나 판단이 안 서면 사용자에게 물어(needsDecision)** "구멍(hole)"을 막는다.
> **성장 전제:** 이 목록은 지속 업데이트된다 — 스펙이 자주 빠뜨리는 고려사항이 발견되면 행을 추가한다. 항목이 늘수록 스펙 생성이 점점 **검증된 형태**로 완성된다.
> **얇게 유지:** 각 항목의 상세 규칙 SOT는 "출처" 열의 ref/스킬이다. 여기선 **목록화·스윕만** 하고 상세는 베끼지 않는다(드리프트 방지).

## 작성 규칙 (불변 — 항목 추가 시 반드시 준수)
- **항목은 반드시 추상 카테고리다.** 특정 use-case(도메인·화면·기능에 종속된 개별 사례)를 항목으로 올리지 않는다. 어떤 페이지·프로젝트에도 적용되는 "점검 축"이어야 한다.
  - ✅ 올바름: `액션→리액션 정합`, `액션 결과 반영의 시점·방식`
  - ❌ 금지: `프로필 수정 후 목록 복귀 시 반영`, `팔로우 후 그 유저 글 노출` — 이런 건 **항목이 아니라 '예:'로만** 붙인다.
- **예시는 이해를 돕는 `예:`로만.** 항목의 "점검 항목/무엇을 확인" 정의 자체는 도메인 무관하게 추상적으로 쓴다.
- 이유: 이 목록은 모든 스펙에 재사용되는 스윕 기준이다. 개별 사례가 항목이 되면 목록이 무한 팽창하고 다른 도메인엔 안 맞아 스윕이 무력해진다.

## 사용법 — 스펙 완성도 스윕
스펙 산출물(requirements/design/tasks/layout-skeleton)을 다 만든 뒤, 아래 각 항목을 스펙과 대조한다:
- **해당사항이 있는데 스펙에 없음 / 확정 불가** → 조용히 넘기거나 지어내지 말고 `needsDecision`(워커) 또는 `AskUserQuestion`(조율자·inline)으로 **처리 방향을 사용자에게 묻는다**.
- **명백히 해당 없음** → 스킵(과질문 금지 — 판단 기준은 `askquestion-principle.md`).
- 반영이 확정되면 대응 FR/섹션으로 emit. 미해소로 남으면 `status: draft`.

## 체크리스트 (FE)
| # | 점검 항목 | 무엇을 확인 | 갭이면 물을 것 | 출처(SOT) |
|---|---|---|---|---|
| C1 | **라우팅/네비게이션** | 라우트 경로·params, 요소 클릭→이동, 이 페이지로 오는 진입점 | 미정 라우트/이동/진입점 | `dt-spec-ask-missing` Step 3.5 · spec-author 게이트 |
| C2 | **자동/비가시 API 호출** | 진입 자동로딩·polling·실시간 구독(WS/SSE)·권한/feature-flag·analytics | 어떤 비가시 호출이 있는지 | `dt-spec-ask-missing` Step 3 (6항목, design doc [4-2](c)) |
| C3 | **짝 없는 능력(orphaned capability)** | API/토큰 등 기반은 있는데 이를 다루는 화면이 없나(역방향: 화면이 없는 상태 전제) | 화면 추가 / 외부·기존 처리 가정 / 범위 제외 / 협의 | `askquestion-principle.md` 예시 A |
| C4 | **액션→리액션 정합** | 생성/수정/삭제/토글이 관련 목록·상세에 반영되나(예: 상세 수정 후 목록 복귀 시 갱신 반영), 뒤로가기 신선도 | 어느 액션이 어디에 반영돼야 하나 | `interaction-integrity.md` §B |
| C5 | **로딩/빈/에러 상태** | 각 데이터 영역에 pending·empty·error UX가 정의됐나 | 미정 상태 UX | `interaction-integrity.md` §B · `dt-frontend-architecture` |
| C6 | **폼 검증·제출 결과** | 입력 검증 규칙·에러 표시·성공 피드백(토스트/이동)이 있나 | 검증 규칙·에러·성공 처리 | (보강 여지 — 신규) |
| C7 | **접근 권한/인증 게이트** | 인증·권한이 필요한 화면이면 미인증·권한없음 처리(리다이렉트/차단)가 있나 | 게이트 동작 | C3·`interaction-integrity.md`(로그인/로그아웃 정합) |
| C8 | **비기능(성능·접근성·i18n·반응형)** | requirements 비기능 절이 채워졌나 | 해당 정책 | `dt-spec-generate-spec` `{{NON_FUNCTIONAL_REQUIREMENTS}}` |
| C9 | **목록 페이지네이션/무한스크롤** | 목록 화면의 페이지네이션 방식·끝 도달·빈 목록 처리 | 방식 선택 | (보강 여지 — 신규) |
| C10 | **액션 결과 반영의 시점·방식** | 액션이 파생 갱신을 유발할 때, 반영 시점·방식(즉시/낙관적 vs 서버 재조회 후 vs 다음 진입 시 vs 수동 새로고침)이 요구사항에 명시됐나 (예: 팔로우 → 그 대상 글이 목록에 즉시 뜨는지 새로고침 후 뜨는지) | 어느 시점·방식으로 반영할지 | `interaction-integrity.md` §B·§C |

> **C4 vs C10 구분:** C4는 반영이 **되어야 하는지**(정합/stale 방지 — 되긴 하나), C10은 반영이 된다면 그 **시점·방식이 미정일 때** 결정을 받는다(즉시 vs 재조회 등). 둘 다 예시일 뿐 항목은 추상.
> **행 추가 방법(작성 규칙 준수):** 새 고려사항은 `[점검 항목 | 무엇을 확인 | 갭이면 물을 것 | 출처]` 한 행으로 추가하되, 위 **작성 규칙(불변)** 대로 **추상 카테고리로만** 올린다(특정 use-case 금지, 예시는 '예:'로). 상세 규칙이 길면 별도 ref로 두고 여기선 한 줄+출처 링크만(이 문서는 얇게).
