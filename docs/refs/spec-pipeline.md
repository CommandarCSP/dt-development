# 스펙 파이프라인 공용 단계 (FE·BE)

FE 페이지 스펙(`dt-spec-generate-spec`)과 BE 리소스 스펙(`dt-bespec-generate-spec`)이 **같이 쓰는 단계의 원본**이다. 두 스킬은 이 문서를 읽고, 자기 스택에만 있는 단계(소스 어댑터·EARS 적응·산출물 본문)를 더한다. 같은 규칙을 두 스킬에 따로 적으면 한쪽만 고쳐져 어긋난다 — 실제로 FR `from:` 결속 규칙이 그렇게 갈라졌었다(GEN-29).

## 1. 스택별 값

| 항목 | FE (`dt-spec`) | BE (`dt-bespec`) |
|---|---|---|
| 단위 | 페이지 `<page>` | 리소스 `<resource>` |
| 산출 위치 | `docs/specs/pages/<page>/` | `docs/specs/resources/<resource>/` |
| 산출물 | requirements · design · tasks · layout-skeleton | requirements · design · tasks · api-contract |
| 워커 | `spec-author` | `bespec-author` |
| `unitRef` | `dt-spec/<page>` | `dt-bespec/<resource>` |
| 소스 어댑터 | Figma(design·wireframe) · 문서 | OpenAPI · 데이터모델(ERD/SQL) · 문서 |
| `deepRead`(상향 정합) | Figma deep-read | OpenAPI·데이터모델 추출 계약 |
| 자기 담당 | FE/공통 SP·IF (BE 전용은 스킵) | BE/공통 SP·IF (FE 전용은 스킵) |
| 중간물 | `.dt-spec/<page>/` | `.dt-spec/<resource>/` |

## 2. 실행 모드 (컨텍스트 경제 — 격리 워커 + needsDecision HITL)

스펙 스킬은 **얇은 조율자**다. 무거운 작업(소스 분석·머지·빌드)은 일회성 워커(§1)가 **자기 컨텍스트에서** 끝내고 포인터+요약만 돌려주게 하여, 조율자(메인 세션) 컨텍스트가 단위마다 부풀지 않게 한다. 모드는 `docs/orchestration-policy.md` 원칙 1·4를 따른다.

- **dispatched (기본 — 서브에이전트 가용 시):**
  1. 조율자가 **§3 정의서 게이트만** 직접 수행한다(스코프 해소·consume/standalone·최소 정의서 생성 여부 등 *시작 전 사용자 결정*은 메인에만 있는 사용자 채널로 묻는다).
  2. `Task`로 워커를 dispatch — `{ <units>, sources, args(--only/--api-doc/--scope), gateResult }` 전달. **여러 단위면 단위별로 병렬 dispatch하지 말고 목록을 한 워커에 넘겨 홀리스틱하게** 짓게 한다 — 그래야 크로스유닛 상호작용(FE: 네비·공유상태·액션→리액션 정합 / BE: 트랜잭션 경계·cascade·스키마 머지 순서)을 한 시야에서 잡고 `docs/specs/interactions.md`의 자기 절을 산출한다. 워커는 스킬의 절차를 단위마다 따르되 사람 결정은 `needsDecision`으로 모아 반환하고 중간물을 §1의 중간물 폴더에 영속화한다.
  3. 조율자는 워커의 작업형 봉투(`{ status, artifacts, needsDecision[], summary, assumptions, units[], interactions, writingLint }` — `docs/orchestration-policy.md` 원칙 5·6)만 받는다(무거운 원자료는 워커 컨텍스트에 격리). `needsDecision`이 비어있지 않으면 **조율자가 AskUserQuestion**(askquestion-principle.md + 원칙 6의 묶음·`recommended`·왕복 상한 2회)으로 묻고 → `answers: [{ id, choice, note? }]`와 함께 워커를 **재dispatch**(워커는 중간물 폴더의 `progress.md`에서 이어서 재개). 비면 완료 보고. 완료 보고의 summary 끝에 `한글 lint: 고침 N·유지 M`(writingLint)을 한 줄로 보인다. 이어서 봉투의 `assumptions`를 "가정 N건 — 바꾸실 게 있으면 말씀해 주세요"와 목록으로 보인다(`docs/refs/askquestion-principle.md` "빈틈 찾기와 묻기 기준"). 사용자가 바꾸는 항목은 `answers`로 받아 같은 워커를 재dispatch한다.
- **inline degrade (원칙 4 — 서브에이전트 미지원 시):** 조율자가 스킬 절차를 **직접** 수행한다. AskUserQuestion도 직접. 워커를 안 거칠 뿐 **같은 절차·같은 산출**.

> 두 모드는 **동일 절차**를 따른다(분기 없음). 차이는 "누가 실행하고 어디서 묻느냐"(격리 여부)뿐 — 정확성 문제가 아니라 컨텍스트 경제 문제.

## 3. §0 정의서 게이트 (소프트)

**먼저 스코프를 해소**(아래 "스코프 해소")한 뒤 `scripts/checkDefinitionGate.mjs`를 `{ projectRoot, scope }`로 호출해 판정(`kind`)을 받고 분기한다(scope 미해소면 `scope` 생략 = bare `definition.md`). **게이트는 판정만, 수락/거절 결정은 여기서 사용자에게 묻는다.** 자동으로 다른 스킬을 호출하지 않는다 — 사용자가 다음 스킬을 직접 실행한다.

**스코프 해소 (다중 스코프 — 어느 정의서를 소비?):** `parseDefinitionSources.discoverDefinitions({ projectRoot })`로 `definition*.md`를 발견한 뒤 다음 **우선순위**로 해소(위에서부터 — 먼저 맞으면 종료):
1. **명시 인자 `--scope <slug>` (최우선)** — 헤더 기록과 **달라도 `--scope`가 이긴다**(잘못 바인딩 교정 통로). 적용 후 leaf 헤더 `scope`를 그 값으로 갱신.
2. **헤더 scope** — `--scope` 없고 leaf 헤더에 `<!-- scope: <slug> -->`가 있으면 → 그 스코프 정의서.
3. **레거시 면제** — scope 헤더·`--scope` 둘 다 없는데 `<!-- basedOnDefinition: N -->`이 있으면 → bare `definition.md`(기존 leaf; basedOnDefinition이 bare 기준으로 찍힘). **질문 안 함.** 잘못 바인딩 시 탈출구 = 1번 `--scope`로 교정.
4. **단일** — `definition*.md`가 정확히 1개면 그걸 사용(스코프 유무 무관).
5. **다중·미지정** — `AskUserQuestion`으로 "이 단위는 어느 스코프?"를 **1회 질문**(자동 추정 금지). 답을 `buildSpecHeader`의 `scope` 필드로 leaf 헤더에 기록(재실행 시 2번에서 회피).

판정별 분기:
- **`consume`**: 정의서 소비. `authorKind:'generated'`면 IF 3분기(`확정`=lock / `미해소`=스펙화 스킵 / 그 외=보강); `authorKind:'hand-authored'`면 값 전부 잠정(IF 합의상태 재확인 시드로만). `migrate:'in-memory'`면 읽기 전용 흡수(정의서 직접 수정 금지). `status:'draft'`면 "미해소 N건, 계속?" 확인 + **미해소 IF 스펙화 스킵 + 참조 SP/기능(BE는 엔드포인트) 자리에 `<!-- skipped: IF-n (미해소) -->` 마커 emit**. consume일 때 `definitionVersion`+`definitionPath`(leaf→정의서 상대경로)+`definitionIfIds`(이 단위가 소비한 IF)를 §4 헤더 빌드로 넘겨 **신규격** `<!-- basedOnDefinition: <상대경로>@v<N> | IF-a,IF-b -->` emit(dt-devspec 「마커 규격」 절 참조) — **이 줄이 쓰기측 규약이자 `extractBasedOnDefinition`(변경 전파)의 입력**이다(손 주석 주입 금지). 이 IF 리스트는 **파일 단위** 결속이다 — IF 리스트 누락 금지. **FR 단위 결속은 §4의 본문 `<!-- from: -->`가 맡는다**(FE·BE 같다 — 생략하지 않는다). 리스트에 있는데 어느 FR도 가리키지 않는 IF는 형식 검사가 `fr-from-missing` 경고로 잡는다.
- **`none`**(정의서 없음): "최소 정의서 만들까요?" **수락**이면 **헤더 없는(hand-authored) 골격 스텁**(추론 IF/SP 전부 `협의중`) 작성 + `/dt-devspec` 안내 — *`Generated by dt-devspec` 마커를 leaf가 달지 않는다*(마커 사칭 금지; 다음 실행에서 hand-authored로 재진입). **거절**이면 standalone(`buildSpecHeader`에 `definitionSOT:'none'`).
- **`needsNormalization`**(대충 손작성): "`/dt-devspec`으로 정규화할까요?" **수락**=산출물 없이 종료(사용자가 `/dt-devspec` 후 재실행). **거절**=standalone(`definitionSOT:'unstructured'`) **+ 대충 정의서 상단에 `<!-- NOT-SOT: unstructured, used as hint by <unitRef> -->` 비파괴 주석을 diff-then-confirm으로 1줄 추가**(idempotent — 이미 있으면 skip; 나중 `/dt-devspec` D12 정규화 복구의 단서이자 거절 재감지 신호 — 헤더 `definitionSOT`와 더불어 재안내 트리거).
- **`corrupt`**: 산출하지 않는다 <!-- hard-stop: 깨진 정의서로 쓰면 잘못된 계약이 스펙에 박힌다(standalone 강등 금지) --> — 이유와 함께 AskUserQuestion(원칙 10): "`/dt-devspec`으로 지금 재생성하고 이어서 실행" / "중단".
- **`versionTooHigh`**: 산출하지 않는다 <!-- hard-stop: 이 플러그인이 모르는 정의서 형식이다 --> — "플러그인 업그레이드 필요(정의서 vN > 지원 vM)"와 업그레이드 방법을 보이고 끝낸다.

IF 사용 규칙:
- 데이터 명세·엔드포인트·스키마를 *추론*하지 말고 정의서의 **IF-n을 합의 상태에 따라** 사용한다:
  - **확정(agreed) IF** → lock. 그대로 인용한다. 재추론·임의 변경 금지.
  - **협의중(tentative) IF** → 잠정 계약이므로 leaf가 deep-read로 **보강·구체화 가능**. 보강 결과는 §6 상향 정합으로 정의서에 환류한다.
- 자기 담당(§1) SP/IF만 스펙화하고 상대 스택 전용 항목은 스킵한다.
- 산출 직전 상향 정합·최종 정합 시 diff의 대조 차원은 `docs/refs/upward-alignment.md` §대조 차원을 따른다(응답 shape 필드·정렬 규약 누락까지 — IF 행 존재만 보지 말 것).

입력 소스 ∩ 자기 어댑터(§1)가 **공집합**이면 스텁이 빈 껍데기라 산출하지 않는다 — 선택지는 스킬마다 다르다(각 스킬의 §0-b).

## 4. 헤더와 역참조

**헤더:** 명령으로 만든다 — `node "${CLAUDE_PLUGIN_ROOT}/scripts/buildSpecHeader.mjs" --status <draft|finalized> --source <type:locator[@role]> [--source …] [--definition <상대경로>@v<N> --if <IF 목록> | --sot none|unstructured] [--scope <s>]`. 이미 쓴 파일은 `--replace <파일>`(헤더 줄만 바꾸고 다른 주석은 남긴다, 빠진 값은 지금 헤더에서). 정의서 버전만 올리는 재결속은 `--replace <파일> --definition <경로>@v<N>` 한 줄이다. 아래는 같은 일을 하는 함수 설명이다 — `scripts/buildSpecHeader.mjs#buildSpecHeader({ generatedAt, status, sources, definitionVersion, definitionPath, definitionIfIds })`로 헤더 블록을 만든다. `sources`는 `ResolvedSource[]` — `[{type, locator, role?, loadFailed?}]` 배열. `definitionVersion`은 **§3 게이트가 반환한 값을 그대로 넘긴다**(consume일 때만; standalone이면 `definitionSOT`). `definitionPath`=leaf→정의서 상대경로, `definitionIfIds`=이 단위가 소비한 IF id 배열. **이 함수가 PLUGIN_VERSION과 specVersion='1.1'을 직접 주입**한다. loadFailed가 true인 소스는 헤더에 `(load-failed)` 노트로 표시된다. `definitionVersion`+`definitionPath` 전달 시 마지막 줄에 신규격 `<!-- basedOnDefinition: <상대경로>@v<N> | IF 리스트 -->`가 자동 추가된다(`definitionPath` 없이 `definitionVersion`만 주면 구 정수형 — 하위호환). brand는 FE·BE 모두 `dt-spec`.

템플릿의 헤더 영역(`<!-- Generated by ... -->`부터 **첫 빈 줄 직전까지 연속된 `<!-- ... -->` 주석 줄 전체** = 헤더 블록의 종료 경계)을 buildSpecHeader 출력 문자열로 **헤더 블록 통째 치환**한다(고정 줄 수에 의존하지 않는다). 헤더 내부 개별 placeholder 치환은 **사용하지 않는다**(이중 치환 방지).

**역참조 emit (변경 전파 입력):** 정의서 항목을 스펙화할 때 출처 역참조를 써넣는다 — **requirements.md의 FR 줄이 기본이다**(design.md 표 행에만 달면 FR 단위 영향 산출이 안 된다). 머리 IF 리스트의 모든 IF가 적어도 한 FR에서 가리켜져야 한다:
- 예) `### FR-2: 파일 검색 ... <!-- from: SP-1 -->`
- API 표 행(FE design.md·BE api-contract.md의 엔드포인트 행) 끝에 `<!-- from: IF-1 -->`

이 역참조가 `definitionPropagation.computeImpacted`의 입력이 되어, 정의서 변경 시 영향받는 FR/엔드포인트를 정밀 산출한다(본문 from-refs + 머리 IF 리스트를 합산). emit하지 않으면 변경 전파가 작동하지 않는다.

## 5. 변경 전파 (정의서 버전 비교)

**§3이 `consume`을 반환했을 때만 적용된다**(standalone=`definitionSOT`이면 비교 기준 정의서가 없어 변경 전파/isStale 전체 비적용). consume일 때:
1. §3 게이트가 반환한 `definitionVersion`(= currentVersion) 사용.
2. 기존 산출물 헤더의 `extractBasedOnDefinition()`(= basedOnDefinition) 획득.
3. `isStale(basedOnDefinition, currentVersion)`가 true면 "영향받는 요구사항/엔드포인트 재검토 필요" 경고.
4. `computeImpacted(changedIds, specMarkdown)`로 정의서에서 바뀐 SP/IF 중 이 spec이 참조하는 것만 정밀 나열. **자동 재작성은 하지 않는다**(diff-then-confirm으로 사용자 확인 후 갱신). 갱신 시 `definitionVersion`+1 + `<!-- updatedBy: <unitRef>@vN -->` provenance + 자기 스펙 `basedOnDefinition`도 동시 갱신(self-stale 회피). **변경 전파와 상향 정합은 별개 쓰기 계기 — 한 실행에서 버전 이중 bump 금지.**
5. **버전만 오른 재결속은 에이전트 없이 한다(GEN-41).** 4의 영향 목록이 비었고 `node "${CLAUDE_PLUGIN_ROOT}/scripts/checkDefinitionDrift.mjs" <정의서> <이 단위 스펙들>`도 0이면 — 이 스펙이 쓰는 IF는 그대로이고 정의서 버전만 올랐다는 뜻이다 — 조율자가 파일마다 `node "${CLAUDE_PLUGIN_ROOT}/scripts/buildSpecHeader.mjs" --replace <파일> --definition <정의서 상대경로>@v<N>`만 돌린다(상태·소스·IF 목록·본문은 그대로). 영향 목록이 있거나 드리프트가 남으면 그때만 작성 에이전트를 다시 부른다. 검증 실행에서 버전만 바뀐 재결속 두 번에 에이전트가 각각 약 10만(환산)을 썼다.

## 6. 상향 정합 (deep-read ↔ 정의서 IF diff) — 게이트 + 쓰기 (T2~T8)

산출 직전, deep-read로 얻은 실제 계약을 정의서 IF와 diff하고 잠정 IF를 승격한다. 전체 절차(T2~T8·D8·H3·compare-and-swap·쓰기 순서)는 `docs/refs/upward-alignment.md`를 Read해 적용한다 — `deepRead`·`unitRef`는 §1. §3이 `consume`(generated)일 때만 적용.

## 7. 상태 결정 — 공통 조건

**형식 검사 먼저:** `node "${CLAUDE_PLUGIN_ROOT}/scripts/validateSpec.mjs" <산출 위치>/*.md`에 오류가 하나라도 있으면 `finalized`가 될 수 없다 — 고치거나 `status: draft`(이유: 형식 오류 N건). 머리 주석이 없거나 옛 `specVersion`인 스펙은 오류가 경고로 낮춰져 막지 않는다. draft 상태는 헤더 메타(`<!-- status: draft -->`)에 표시 — 다른 도구가 이를 인식하고 경고. 스택별 draft 트리거는 각 스킬에 있다.

## 8. 파일 저장 — 재실행 정책 (dt-spec 설계 §8-4)

산출 위치(§1) 디렉토리:

| 시나리오 | 정책 |
|---|---|
| 디렉토리 없음 | 신규 생성 + 산출물 4개 작성 |
| 디렉토리 있음 + 동일 단위 | 기존 산출물 헤더의 sources를 `parseSpecHeader`로 복원해 이번 sources와 union → 새 결과와 기존 산출물 diff 표시 → 항목별 confirm → 동의 시 갱신, 거부 시 기존 유지 |
| 일부 산출물만 갱신 요청 (`--only requirements` 등) | 해당 파일만 처리. **다른 파일(헤더 포함)은 일절 건드리지 않음** — 헤더 버전 혼합 허용(parseSpecHeader가 파일별 버전 독립 파싱). 전체 디렉토리를 specVersion 1.1로 올리려면 `--only` 없이 전체 재실행. |
| 사용자가 산출물 직접 편집 후 재실행 | 사용자 편집 우선 — 누락 부분만 추가 (diff 후 confirm) |

**핵심 원칙**: 자동 덮어쓰기 금지. 이 재실행 정책은 산출물 4개 모두에 동일하게 적용된다. 스택별 예외(FE 스텁/구조 스켈레톤 전환)는 각 스킬에 있다.

## 9. 완료 후 — 능동 요약 알림 (D5 ②)

매 산출/standalone 종료 시: standalone(`definitionSOT: none|unstructured`)이면 고정 `⚠ 정식 SOT 없이 작성됨(일관성 미보증) — /dt-devspec 정식화 권장`. consume이면 자기 스펙이 의존하는 IF 중 `협의중`/`컨벤션` 잔존 시 `ℹ 협의중/컨벤션 M건 — BE 상향정합(T2/T3) 시 확정`(M은 from-ref·basedOnDefinition 필터로 자기 의존분만; standalone info는 자기 본문 협의중/컨벤션 IF 수). nag+info 동시면 ` · `로 병기. 산출하지 않고 끝난 실행(corrupt/versionTooHigh/공집합)은 원칙 10의 선택지로 갈음(이 알림 비적용).
