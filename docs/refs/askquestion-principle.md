# 참조: askQuestion 작성 원칙 (모든 AskUserQuestion 공통)

> 종류: **참조 문서(지식)** · 소비처: `dt-spec-generate-spec`, `dt-spec-ask-missing`, `dt-bespec-ask-missing`, `dt-spec-collect-project-context`, `spec-author`·`bespec-author`·`definition-author`·`plan-author` 에이전트, 그리고 질문하는 모든 조율자.
> SOT: 본 문서. (이전엔 `dt-spec-ask-missing` SKILL.md가 원본이었고 다른 스킬이 그걸 가리켰음 — ask-missing 해체에 대비해 ref로 승격.)

AskUserQuestion 호출 시 사용자가 "무엇을, 왜 설정하는지" 즉시 이해하도록 맥락을 충분히 담는다. **질문 한 줄 + 라벨만 있는 옵션은 금지** (사용자가 의도를 파악 못 함).

각 질문은 3요소를 포함한다:
1. **배경(Why)** — 왜 묻는지 + 현재 페이지/기능 맥락. `question` 첫 문장에 실제 페이지명·추출된 요소명을 넣어 구체화 (예: "이 페이지(SCR_FLE_01 파일관리)의 **login_button**에서 ...").
2. **영향(Impact)** — 이 답이 어느 산출물(requirements.md FR / design.md / tasks.md)에 어떻게 반영되는지 `question`에 명시 (예: "선택한 항목은 requirements.md에 Event-driven FR로 추가됩니다").
3. **옵션 설명(Options)** — 각 `option`의 `description`에 구체적 의미 + 선택 시 결과 + 예시. label만 두지 말 것.

도구 사용 팁:
- `header`: 짧은 주제 태그 (예: "API 후보", "접근 권한", "비기능 요구").
- 항목이 4개를 초과하면 여러 질문으로 분할하거나 `multiSelect: true` 사용 (AskUserQuestion 옵션 최대 4개).
- method/endpoint/schema 같은 **자유 값 입력**은 옵션으로 강제하지 말고, `question`에 입력 형식과 예시를 충분히 제시한 뒤 사용자의 텍스트 답변("Other")을 받는다.

## 무엇을 "애매함"으로 보고 물을 것인가 (판단 예시)

위가 "어떻게 잘 묻나"라면, 아래는 **언제 물어야 하나** — 조용히 넘기거나 임의로 지어내지 말고 `needsDecision`(워커) 또는 AskUserQuestion(조율자)으로 올려야 하는 대표 애매함. **판단 기준: "스펙만으로 한 가지로 확정되지 않고, 추측하면 사용자 의도와 어긋날 수 있다"면 묻는다.**

### 예시 A — 짝 없는 능력 (orphaned capability, 필수 감지)
**한쪽에 능력/계약이 있는데 그것을 소비·노출하는 짝이 스펙에 없을 때.**
- 전형: **BE에 인증 기반(로그인/토큰 발급 API, JWT 처리, 세션)은 있는데 이를 다루는 FE 화면 스펙(로그인/로그아웃/토큰 만료 처리 UI)이 없음.** (역방향도 동일 — UI가 인증 상태를 전제하는데 인증 API가 없음.)
- **하면 안 되는 것:** 로그인 화면을 임의로 만들어 넣기(과생성) / 인증을 조용히 무시하고 나머지만 구현(침묵 누락). 둘 다 사용자 의도와 어긋날 수 있다.
- **물어야 함(needsDecision):**
  - `topic`: "인증 기반(API/JWT)은 있으나 이를 다루는 화면 스펙이 없습니다. 어떻게 처리할까요?"
  - `options` 예: `"로그인/로그아웃 화면 스펙을 추가한다"`(→ 페이지 스펙 신설) / `"인증은 기존/외부 흐름이 처리한다고 가정"`(→ 화면 미생성, 토큰 주입만 전제) / `"이번 범위에서 제외"`(→ 해당 API는 stub·미노출로 표기) / `"별도 협의 필요"`.
  - `evidence`: 어느 계약(예: `POST /auth/login`, `Authorization: Bearer`)이 소비처 없이 떠 있는지.
  - `reflectsTo`: 정의서 IF / 해당 페이지·리소스 스펙.
- 일반화: 능력↔소비처가 1:0으로 뜨면(엔드포인트에 대응 화면 없음, 화면이 없는 상태 전제) 그 갭을 **명시적으로 surface**한다.

## 빈틈 찾기와 묻기 기준 (스펙·정의서·플랜 작성 공통)

위 예시 A처럼 **정해진 점검 목록**에 걸리는 것만 묻으면, 목록 밖의 빈틈은 조용히 메워지거나 TODO로 남아 뒤 단계가 추측한다. 사람과 일할 때처럼, 쓰기 전에 **"소스에 없는데 내가 채워야 하는 자리"**를 스스로 찾아 하나씩 판단한다.

### 1. 가정 목록을 먼저 만든다

산출물을 쓰기 전에(또는 쓰면서) 채워야 하는데 소스가 말해 주지 않는 자리를 모두 적는다. 다음을 훑으면 대부분 걸린다.

- **상태:** 빈 목록, 로딩, 실패, 권한 없음, 오프라인, 첫 사용
- **경계:** 최대·최소 길이와 개수, 중복, 동시 수정, 페이지 끝
- **되돌리기:** 삭제가 바로 지우는지·숨기는지, 취소·실행 취소, 확인 단계
- **권한:** 누가 보고 누가 바꾸나, 남의 것을 열면 어떻게 되나
- **흐름:** 성공·실패 뒤 어디로 가나, 다른 화면·리소스에 무엇이 반영되나
- **값:** 정렬 기준, 기본값, 시간대·형식, 문구

### 2. 자리마다 세 갈래로 나눈다

| 분류 | 언제 | 하는 일 |
|---|---|---|
| **근거 있음** | 소스·기존 코드·`project-context.md`·정의서·앞서 받은 답으로 한 가지로 정해진다 | 묻지 않는다. 근거(파일:줄·원문)를 대고 쓴다 |
| **가정하고 알림** | 사용자에게 보이는 결과가 크게 안 바뀌고, 관례나 기존 패턴이 분명하다 | 가정대로 쓰고 그 줄에 `[inferred]`를 단다. 반환의 `assumptions`에 올린다 |
| **묻기** | 아래 "묻는 기준"에 하나라도 걸린다 | 쓰지 않고 `needsDecision`으로 올린다(원칙 6). 권장안과 이유를 함께 낸다 |

**묻는 기준** — 하나라도 맞으면 묻는다.
- 사용자에게 보이는 동작이나 화면 흐름이 달라진다
- 데이터가 지워지거나, 보존 기간·공개 범위가 달라진다
- 권한·보안·결제처럼 틀리면 사고가 나는 자리다
- API 계약(경로·필드·상태 코드)이나 다른 화면·리소스와의 연결이 달라진다
- 나중에 바꾸기 어렵다(스키마, 라우트, 외부 공개 값)
- 그럴듯한 해석이 둘 이상이고 어느 쪽인지 근거가 없다

**지어내지 않는다.** 값·문구·엔드포인트·에셋은 가정 대상이 아니다. 근거가 없으면 묻거나, 끝까지 비면 `TODO` + `status: draft`로 남긴다.

**질문 수를 아낀다.** 같은 원인에서 나온 빈틈은 한 질문으로 묶는다(예: "삭제 3곳 모두 휴지통 방식인가"). 한 단위에서 묻기가 많으면 기초 결정(되돌림 정책·권한 모델)을 먼저 묻고, 파생 질문은 답을 받은 뒤 다시 판단한다.

### 3. 예시

- **예시 A — 짝 없는 능력:** 위 절 참조.
- **예시 B — 스펙 빈틈:** 기획서에 "게시글 삭제" 버튼만 있고 삭제 뒤 동작이 없다. 휴지통인지 바로 삭제인지는 데이터가 사라지느냐가 달라지니 **묻는다**. 삭제 후 목록으로 돌아가는 것은 기존 화면이 모두 그렇게 하면 **가정하고 알린다**.
- **예시 C — 내용 불일치:** 기획서는 닉네임 최대 10자, Figma 입력창 힌트는 20자. 어느 쪽도 고르지 않고 **묻는다**. `evidence`에 양쪽 원문을 인용한다.
- **예시 D — 기술 불일치:** 플러그인 기본은 Tailwind인데 프로젝트는 SCSS 모듈을 쓴다. 기존 코드가 한 방식으로 일관되면 **그 방식을 따르고 알린다**(`assumptions`). 기존 코드끼리도 갈려 있으면 어느 쪽으로 맞출지 **묻는다**.

### 4. 답과 가정을 남기는 곳

- 받은 답과 가정은 `reflectsTo`가 가리키는 **산출물의 그 절에 반영**한다. 반영된 본문이 곧 기록이다. 따로 결정 목록 파일을 만들지 않는다(오래 남는 결정 문서는 로드맵 GEN-21).
- 재실행 때 이미 반영된 결정은 **다시 묻지 않는다.** 입력 소스가 바뀌어 그 결정의 근거가 흔들릴 때만 다시 판단한다.
- `assumptions` 항목 모양: `{ id, what: "<무엇을 가정했나>", why: "<근거·관례>", reflectsTo }`. 조율자는 완료 보고에 "가정 N건"과 목록을 보이고, 사용자가 바꾸고 싶은 항목은 `answers`로 받아 같은 에이전트를 재dispatch한다.
