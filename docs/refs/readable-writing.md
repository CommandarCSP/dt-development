# 참조: 읽기 좋은 글쓰기 (Jira/Confluence 공통)

> 종류: **참조 문서(지식)** · 소비처: 계층 1(산문) `dt-worklog-sync`·`dt-confluence-doc`·`dt-explain` → `agents/ko-writing-reviewer.md`가 이 문서로 판정 · 계층 2(내부 구조 문서) `spec-author`·`bespec-author`·`definition-author`·`plan-author`·`dt-e2e`·`dt-be-e2e` → `scripts/koWritingLint.mjs`로 자기 수정.
> SOT: 본 문서. 플러그인이 생성하는 모든 한글 글의 문장 규율을 한곳에서 정의한다. 깊은 판정 근거는 `rules/vendored/yoonmoon/`(번역투 8종·AI 티 11종 원문).

## 대원칙

> 이 프로젝트를 오늘 처음 본 사람이, 따로 물어보지 않고 이해할 수 있게 쓴다.

글은 "무엇을 했는지"를 넘어 **처음 보는 독자가 따라 읽을 수 있는지**를 기준으로 다듬는다.
아래 규칙은 세 묶음이다. A는 이해를 막는 요소를 없애고, B는 문장 자체를 매끄럽게 만들고,
C는 우리말답지 않은 티를 지운다.

### 낱말 하나로 판정할 때 — 이 질문 하나면 된다

> **이 낱말을 동료에게 말로 설명할 때 쓰겠는가.**

안 쓰면 바꾼다. "틀렸는가"가 아니라 **"입으로 나오는가"**가 기준이다. `시간이 자랍니다`는
문법도 뜻도 멀쩡하지만 옆자리에 대고 그렇게 말하지는 않는다. 그래서 바꾼다.

아래 표들을 외우는 것보다 이 질문 하나를 대 보는 쪽이 실전에서 빠르다. 표는 자주 걸리는
것을 모아 둔 것이지 금칙어 목록이 아니다.

### 관용구로 굳은 것은 그대로 둔다

규칙은 낱말이 아니라 **쓰임**을 본다. 아래는 일상어이므로 고치지 않는다.

- `그 자리에서 취소하세요` · `한자리에서 봅니다` — C3 의 「자리」와 모양이 같지만 관용구다.
- `백그라운드에서 돌아갑니다` — C3 의 「돌다」와 같지만 일반 사용자에게도 통한다.
- `목록에 쌓이고` — 의인화가 아니라 굳은 표현이다.

기계적으로 치환하면 이런 것까지 바꾸게 된다. 걸릴 때마다 위 판정 기준을 한 번 대 본다.

## 묶음 A — 이해 장벽 제거

**A1. 약어·이니셜은 첫 등장에서 풀어쓴다.**
`풀이(약어)` 형식으로 한 번 풀고, 이후에는 약어만 써도 된다.
- 나쁨: `SOT 상향정합 게이트를 강제화했다.`
- 좋음: `단일 진실 원천(SOT)에 맞추는 검증 단계를 필수로 만들었다.`
- 자주 나오는 예: 완료 조건(DoD), 단일 진실 원천(SOT), 인터페이스(IF), 데이터 전송 객체(DTO), 프론트엔드(FE)·백엔드(BE).

**A2. 내부 용어·파일명에는 한 줄 설명을 붙인다.**
팀·파이프라인 안에서만 통하는 말은 처음 나올 때 무엇인지 밝힌다.
- 나쁨: `definition.md 기준으로 반영했다.`
- 좋음: `FE/BE 범위를 나눈 정의서(definition.md)를 기준으로 반영했다.`

**A3. 결과에는 배경을 한 줄 붙인다.**
무엇을 왜 했는지 최소 한 줄. "왜(Why)" 슬롯을 비우지 않는다.
- 나쁨: `주문 취소 API 추가.`
- 좋음: `고객이 배송 전 주문을 스스로 취소할 수 있도록 주문 취소 API를 추가했다.`

## 묶음 B — 문장 다듬기

**B1. 문체를 하나로 통일한다.**
문서 타입별 어투를 고정하고 한 글 안에서 섞지 않는다.

| 문서 | 독자 | 문체 | 추가 규율 |
|---|---|---|---|
| Jira 설명·코멘트 | 팀 내부 | 개조식(명사·서술 종결) | 성분·조사를 뭉개지 않는다 — 개조식이어도 "무엇을 왜"가 읽혀야 한다 |
| Confluence 산문 | 팀·조직 내부 | "~합니다" 정중체 | — |
| 문제 설명 답변(dt-explain) | 요청자 | "~합니다" 정중체 | 근거 라벨(🟢/🟡)은 answer-frame이 정한다 |
| 사외 사용자 가이드 | 제품을 처음 보는 일반 사용자 | "~합니다" 정중체 + 쉬운 말 | 2인칭('여러분'·'당신'·'사용자님') 회피 — 필요하면 주어 생략. 개발 용어 첫 등장 풀이 필수(C3). 사내 시스템·티켓 키 언급 금지 |
| 인수인계 핸드북 (`docs/handbook/handbook.md`) | 코드를 물려받는 개발자 | 평서체("~한다") | **묶음 D 적용**. 개발 용어는 풀지 않는다(A1 면제), 이모지 금지, 지시문 금지 |
| 내부 구조 문서 (requirements·design·api-contract·definition·E2E 시나리오 원장·plan) | 같은 팀 개발자 | 평서체("~한다") | **한글 서술에** 묶음 B·C 적용 — 페이지 목적·사용자 스토리·Given-When-Then·결정 근거, 그리고 **EARS 줄의 한글 부분**(`THE SYSTEM SHALL` 뒤의 서술도 사람이 읽는 본문이다). **검사 대상 아님**: EARS 키워드 자체(`WHEN`·`THE SYSTEM SHALL` 등 — 마스킹), 요소·엔드포인트 목록 줄, `[ai-confirmed]` 같은 라벨, `<!-- … -->` 주석 |

**B2. 주어를 살리고 능동태로 쓴다.**
누가 무엇을 했는지 분명히 한다. 무주어·수동 표현을 피한다.
- 나쁨: `검증이 처리됨. 게이트가 강제화 진행.`
- 좋음: `백엔드가 요청을 검증하고, 최종 게이트를 필수로 적용한다.`

**B3. 명사화와 군더더기를 푼다.**
"~를 수행/처리함" 같은 한자어 명사 나열을 동사로 풀고, 없어도 되는 말은 지운다.
- 나쁨: `데이터에 대한 검증의 수행을 통한 정합성 확보.`
- 좋음: `데이터를 검증해 정합성을 맞춘다.`

**B4. 한 문장에 한 개념, 두 줄을 넘기지 않는다.**
문장이 길어지면 자른다. 기호(→, ·) 나열로 문장을 대체하지 않는다.
- 나쁨: `로그인 → 토큰 발급 → 캐시 저장 → 응답, 실패 시 롤백 처리 및 로깅.`
- 좋음: `로그인에 성공하면 토큰을 발급해 캐시에 저장한 뒤 응답한다. 실패하면 롤백하고 로그를 남긴다.`

## 묶음 C — 우리말답게 (AI·번역 티 제거)

**C1. 기계에 사람 행위를 붙이지 않는다 (의인화).**
무생물 주어(앱·화면·버튼·트레이·설정·서버·기능·시스템·프로그램·서비스·모듈)에 **사고·감정·의사소통 동사**를 붙이지 않는다. 기계 동작을 서술하는 동사는 허용한다. 판단 기준: "이 동사를 기계가 한다고 말해도 이상하지 않은가." 이상하면 위반이다.

| 금지 동사 (예) | 허용 동사 (예) |
|---|---|
| 알려 주다, 말하다, 기억하다, 이해하다, 판단하다, 원하다, 기대하다, 도와주다, 챙기다, 품다, 고민하다, 신경 쓰다, 노력하다 | 표시하다, 보여 주다(화면이 그림을), 저장하다, 열다/닫다, 실행하다, 보내다/받다, 만들다, 지우다, 바꾸다, 확인하다(검사 의미), 처리하다 |

- 나쁨: `작업이 멈춘 것인지 트레이가 알려 줍니다.`
- 좋음: `작업이 멈추면 트레이에 그 상태가 표시됩니다.`
- 나쁨: `앱이 필요한 것을 이미 품고 있습니다.`
- 좋음: `필요한 구성 요소는 앱에 이미 들어 있습니다.`

**C2. 영어 구문을 직역한 티를 지운다 (번역투).**

| 패턴 | 나쁨 | 좋음 |
|---|---|---|
| `~에 의해` 피동 | 설정에 의해 결정됩니다 | 설정이 정합니다 |
| `~을/를 통해` 경로 도식 | 설정 화면을 통해 바꿀 수 있습니다 | 설정 화면에서 바꿀 수 있습니다 |
| `~에 있어(서)` | 사용에 있어 주의할 점 | 쓸 때 주의할 점 |
| `~에 대해/대한` 남용 | 오류에 대해 확인합니다 | 오류를 확인합니다 |
| 이중 피동 `~되어지다/보여지다` | 저장되어집니다 | 저장됩니다 |
| `~중 하나` (one of) | 가장 중요한 기능 중 하나입니다 | 특히 중요한 기능입니다 |
| 직역 대명사 `그것/그들/이것은` | 그것은 다음 질문부터 적용됩니다 | 다음 질문부터 적용됩니다 |
| 무생물 복수 `-들` | 파일들을 넣으면 | 파일을 넣으면 |
| `~을 가지다` (have) | 두 가지 방식을 가집니다 | 두 가지 방식이 있습니다 |
| `~로 인한/인해` | 오류로 인해 멈춥니다 | 오류 때문에 멈춥니다 |

`~을 통해`·`~에 대해`는 실제 경로·대상을 뜻할 때는 자연스럽다("네트워크를 통해 전송"). **대체어로 바꿔도 뜻이 같으면** 위반으로 본다.

**C3. 평소에 안 쓰는 말을 쓰지 않는다 (낯선 용어).**
일상어가 있으면 일상어를 쓴다. 시작 치환표(문맥에 따라 예외 가능):

| 낯선 말 | 일상어 |
|---|---|
| 수행하다 | 하다 |
| 존재하다 | 있다 |
| 해당 (명사 앞) | 그, 이 |
| 확보하다 | 마련하다, 갖추다 |
| 소요되다 | 걸리다 |
| 발생하다 | 생기다, 나다 |
| 제공하다 | 주다, 있다 (사외 문서) |
| 완료되다 | 끝나다 |
| 요구되다 | 필요하다 |
| 활용하다 | 쓰다 |
| 위치하다 | 있다 |
| 진행하다 (단독) | 하다 |
| 기인하다 | ~ 때문이다 |
| 도출하다 | 얻다, 뽑다 |
| 제공하다 (사외 문서) | 주다, 있다 |
| 선택 가능하다 | 고를 수 있다 |

사외 독자용 문서(사용자 가이드)에서는 개발 용어(빌드·배포·인스턴스·캐시·토큰)를 **첫 등장에서 풀어 쓰거나** 일상어로 바꾼다. 내부 문서에서는 A1·A2가 이미 다룬다.

**C3-b. 평범한 낱말이 있는데 굳이 고른 말을 쓰지 않는다 (문학적 어휘).**
C3 이 "어려운 말"이라면 이쪽은 "멋 부린 말"이다. 뜻은 맞지만 말로는 안 하는 것들이다.

| 쓰지 않는다 | 대신 |
|---|---|
| 고르는 **자리**는 | 고르는 **곳**은 |
| 문서가 저장된 **자리** | 문서가 저장된 **위치** |
| 설정은 두 **층**입니다 | 설정은 두 **종류**입니다 |
| 그 시간이 **자랍니다** | 그 시간이 **늘어납니다** |

**C3-c. 개발자끼리 쓰는 구어를 문서로 내보내지 않는다 (뜻이 흐린 구어).**

| 쓰지 않는다 | 대신 |
|---|---|
| 그 모델로 **돕니다** | 그 모델을 **씁니다** |
| 정비는 … 때만 **돕니다** | 정비는 … 때만 **실행됩니다** |
| 문서를 **먹은** 항목 | 문서를 **넣은** 항목 |

위 셋은 `koWritingLint` 가 잡지 못한다 — 같은 낱말이 관용구로도 쓰이기 때문에
기계가 가르면 오탐이 쏟아진다. **리뷰어(사람·AI)가 판정 기준을 대 본다.**

**C3-d. 영어 개발 은어를 그대로 옮기지 않는다 (번역체 동사).**
C3-c 가 우리말 구어라면 이쪽은 **영어 은어의 직역**이다. 개발 맥락이라고 허용되지 않는다 —
뜻이 그대로인 우리말이 있기 때문이다. 아래는 맥락이 좁아 기계가 가릴 수 있어 `koWritingLint`
가 검사한다(산문 문서 공통).

| 영어 | 직역 (쓰지 않는다) | 대신 |
|---|---|---|
| bake into | 배포물에 **굽는다** | 빌드할 때 설치본에 **함께 넣는다** |
| emit·leak | 로그를 **흘린다** | 로그를 **내보낸다** |
| die·kill | 프로세스가 **죽는다** | 프로세스가 **멈춘다** |
| drop | 요청을 **떨어뜨린다** | 요청을 **버린다** |
| hit·step on | 같은 함정을 다시 **밟는다** | 같은 함정에 다시 **걸린다** |
| fire·shoot | 요청을 **쏜다** | 요청을 **보낸다** |
| take a path | 증분 경로를 **탄다** | 증분 경로를 **쓴다** |
| piggyback | 응답에 **태워 보낸다** | 응답에 **실어 보낸다** |

백틱 안(코드·식별자)은 검사하지 않는다.

**C4. AI가 쓴 글의 버릇을 지운다.**

| 버릇 | 나쁨 | 좋음 |
|---|---|---|
| 상투 도입구 | 결론적으로 / 주목할 점은 / 흥미롭게도 / 종합하면 / 요컨대 | (지우고 본론으로) |
| 문두 접속사 반복 | 또한 ~. 따라서 ~. 또한 ~. | 흐름으로 잇고 접속사는 꼭 필요한 곳 한 번 |
| 형식명사 종결 | 확인하는 것이 중요합니다 | 확인해야 합니다 |
| 강조 부사 남발 | 매우 중요하고 정말 유용합니다 | 중요합니다 |
| `-적` 연쇄 | 기술적 토대의 구조적 측면 | 기술 기반의 구조 |
| 영어 병기 과다 | 프레임워크(framework)를 (매번) | 첫 등장만 병기, 이후 한국어 |
| 균일한 리듬 | 모든 문장이 같은 길이·같은 종결 | 짧은 문장과 긴 문장을 섞음 |
| 홍보 어휘 | 강력한 / 혁신적인 / 놀라운 | 구체적 사실로 |

## 보존 원칙 (리뷰·수정 공통)

고치는 쪽이 지켜야 할 불변:
- 고유명사, 수치·단위·날짜, 코드 식별자·명령어·파일 경로, 인용문은 한 글자도 바꾸지 않는다.
- 주장의 방향과 강도를 바꾸지 않는다("항상"을 "대개"로 바꾸지 않는다).
- 격식체 수준을 바꾸지 않는다(정중체 → 평서체 금지).
- **과교정 가드**: 한 문단에서 바뀐 문장이 절반을 넘으면 그 문단은 고치지 않고 `확인 요망`으로 표시해 사람에게 넘긴다.

## before / after 예시

**예시 1 — 커밋 요약(Jira 설명, 개조식):**
- before: `SOT 상향정합 최종 게이트 강제화 (BE). definition.md 기준 IF 계약 반영.`
- after:
  ```
  무엇을: 백엔드에서 단일 진실 원천(SOT)에 맞추는 최종 검증 단계를 필수로 만듦.
  왜: FE/BE 범위를 나눈 정의서(definition.md)의 인터페이스(IF) 계약과 실제 코드가 어긋나는 것을 막기 위해.
  ```

**예시 2 — 작업 요약(Confluence 산문, 정중체):**
- before: `스캐폴드 도메인 3개 추가, 리뷰 게이트 통과. FE 5레이어 배선 완료.`
- after: `코드 생성기(스캐폴드)로 도메인 3개를 새로 추가했고, 자동 리뷰 검사를 통과했습니다. 프론트엔드(FE)의 5개 계층(페이지·도메인·훅·스토어·유틸) 연결도 마쳤습니다.`

## 묶음 D — 개발자 문서(handbook)

`dt-handbook` 이 만드는 인수인계 핸드북에만 적용한다. 독자가 개발자이므로 사용자 문서 규칙을
그대로 씌우면 정확도를 잃는다. `koWritingLint(text, { docType: 'handbook' })` 이 기계 검사를,
`ko-writing-reviewer`(`docType: 'handbook'`)가 판정을 맡는다.

### 그대로 유지
B2 능동태 · B3 명사화 풀기 · B4 한 문장 한 개념 · C2 번역투 · C3 낯선 말(`수행하다`→`하다`) ·
C3-c 개발자 구어 · C4 AI 티.

### 완화

| 규칙 | 사용자 문서 | 핸드북 |
|---|---|---|
| A1 약어 풀이 | 전부 풀이 | 일반 개발 상식(API·DTO·IPC·DOM·CI)은 면제. 이 프로젝트에서만 통하는 말만 풀이 |
| C1 의인화 | 판단·결정 동사 금지 | **알고리즘 서술은 허용** — `라우터가 경로를 판단한다`는 정상. `앱이 사용자를 이해한다`는 여전히 위반 |
| C3 개발 용어 | 일상어로 바꾼다 | **대체 불가능한 용어(명사·식별자)만** 그대로 쓴다 — `IPC`·`캐시`·`토큰`은 풀어 쓰면 틀린 글이 된다. **동사·비유·관용구는 면제가 아니다** |

면제의 경계를 헷갈리면 안 된다. 실제로 "개발 용어는 그대로"라는 한 줄 때문에 개발자 말투 전체가
통과한 판이 있었다.

| 면제 (그대로 쓴다) | 면제 아님 (고친다) |
|---|---|
| 대체할 우리말이 없는 용어 — `IPC`·캐시·토큰·프런트매터 | 번역체 동사 — 배포물에 **굽는다**(bake) → 빌드할 때 설치본에 **함께 넣는다** |
| 코드에 그 이름으로 있는 식별자 — `AbortController`·`withProjectLock` | 개발자 구어 — 진행을 화면에 **흘린다** → **내보낸다** |
| 세는 단위·규약 이름 — 채널·훅·잡 | 멋 부린 외래어 — **파사드**는 → 측정값을 보내는 **코드**는 |

판정 기준은 하나다. **그 말을 한국어로 바꿨을 때 뜻이 달라지는가.** 달라지면 용어라 남기고,
안 달라지면 번역체라 고친다. `IPC` 를 "프로세스 간 통신"으로 바꾸면 채널 규약을 가리키는 힘이
사라진다 — 그래서 남긴다. `배포물에 굽는다` 를 `빌드할 때 함께 넣는다` 로 바꾸면 뜻이 똑같다 —
그래서 고친다.

### 추가

**D1. 왜를 비우지 않는다. 그리고 한 마디로 압축하지 않는다.**
"왜"를 한 구절에 욱여넣으면 쓴 사람만 아는 수수께끼가 된다. **원인 → 그래서 생기는 일 → 안
지키면 벌어지는 일** 가운데 최소 둘을 문장으로 이어야 독자가 납득한다.
- 나쁨: `이 계층은 IPC 로만 통신한다.` (왜가 없다)
- 부족: `의도된 공유다 — 두 벌로 두면 한쪽만 고쳐질 자리다.` (압축이 심해 무슨 말인지 모른다)
- 좋음: `두 흐름이 같은 함수를 부른다. 복사 규칙이 한 곳에만 있어야 하기 때문이다. 함수를 두 벌로 두면 한쪽만 고치는 일이 생기고, 그때부터 프로젝트를 만들 때와 파일을 넣을 때의 결과가 달라진다.`

**D8. 처음 보는 사람 기준으로 자립하게 쓴다 (독자 시험).**
가장 자주 나오는 결함은 낱말이 아니라 **전제**다. 쓴 사람이 이미 아는 것을 독자도 안다고 여기면,
문장은 다 맞는데 읽는 사람은 납득하지 못한다. 문단 하나를 끝낼 때마다 다섯 질문을 대 본다.
하나라도 "아니오"면 그 문단은 아직 안 끝났다.

1. **주장이 한 문장으로 나오나.** 이 문단이 무엇을 말하려는지 스스로 요약할 수 없으면 아직 생각이 안 끝난 것이다.
2. **왜가 결론이 아니라 사실로 적혀 있나.** "의도된 것이다"·"그렇게 설계했다"는 이유가 아니라 이유의 이름표다. 무엇 때문에 그렇게 됐는지를 적는다.
3. **어긋나면 무엇이 눈에 보이나.** 규약·경계·공유를 설명했으면 그것이 깨졌을 때 사람이 관찰하는 증상을 적는다. 증상이 없으면 독자는 그 규약을 지킬 이유를 못 느낀다.
4. **처음 보는 낱말을 풀었나.** 이 프로젝트에서만 쓰는 말(모듈·잡·보관함·근거 소스처럼 흔한 낱말을 특별한 뜻으로 쓰는 경우 포함)은 첫 등장에서 한 줄로 푼다. 일반 개발 용어는 풀지 않는다(A1 면제).
5. **숫자에 기준이 있나.** 숫자만 적으면 큰지 작은지 모른다. 무엇을 재서 나온 값인지, 무엇과 견주는 값인지를 함께 적는다.

예 — 실제로 고친 문단이다.

- 나쁨: `의도된 공유다 — 같은 폴더에 같은 규칙으로 복사하는 일이라 두 벌로 두면 한쪽만 고쳐질 자리다.`
  (2번 실패: "의도된"이 이유를 대신한다. 3번 실패: 한쪽만 고치면 무슨 일이 생기는지 없다)
- 좋음: `일부러 그렇게 뒀다. 두 경우 모두 하는 일이 똑같기 때문이다 — 프로젝트 폴더 안 정해진 자리에 파일을 복사하고, 이름이 겹치면 바꾸고, 참조 문자열을 돌려준다. 이 규칙이 두 벌로 나뉘어 있으면 한쪽만 고치는 일이 반드시 생긴다. 그러면 프로젝트를 만들 때 넣은 파일과 나중에 넣은 파일이 서로 다른 규칙으로 들어간다.`

- 나쁨: `실측으로 원본 2개짜리 보관함을 컴파일하는 데 59턴이 들었다.`
  (5번 실패: 59턴이 많은지 적은지, 무엇을 한 번 세는 단위인지 모른다)
- 좋음: `실측으로 원본 2개짜리 보관함을 컴파일하는 데 에이전트 왕복이 59번 필요했다. 원본이 늘면 이 값이 그대로 늘어난다 — 100개짜리 보관함은 몇 분이 아니라 몇십 분 단위가 된다.`

- 나쁨: `경로 계산이 어긋나면 CLI 가 조용히 빈 목록을 돌려준다.`
  (3번은 있으나 4번 실패: "조용히"가 무슨 뜻인지, 왜 오류가 안 나는지 없다)
- 좋음: `한쪽만 바뀌면 두 진입점이 서로 다른 폴더를 보게 되는데, 이때 오류가 나지 않는다. 없는 폴더를 읽으면 그냥 프로젝트가 하나도 없는 것으로 보인다.`

**D7. 문서를 만든 과정을 문서에 쓰지 않는다.**
독자는 우리가 **어떻게 알아냈는지**가 아니라 **코드가 어떤지**를 읽는다. 분석 도구 이름, 중간
산출 파일, 도구가 붙인 꼬리표는 전부 뺀다. 근거로 자기 산출물을 인용하는 것도 순환이라 안 된다.
- 나쁨: `분석 스크립트는 파일 쓰기를 file:fs 한 덩어리로 뭉쳐 "주인이 둘" 판정을 못 냈다.`
- 좋음: (그 문장을 지우고) `저장소마다 쓰는 쪽은 하나씩이다.`
- 나쁨: `> 근거 — 문서 docs/handbook/structure.json 핫스팟`
- 좋음: `> 근거 — 코드 src/agent/bridge.ts · git 최근 12개월 변경 이력`

**D2. 대안과 반례를 적는다.** 물려받는 사람에게 가장 값나가는 정보다.
- 좋음: `직접 호출로도 되지만, 창이 여러 개일 때 순서가 깨져서 큐를 뒀다.`

**D3. 단정에는 근거, 추정에는 라벨.** 뱃지 세 가지만 쓴다 — `[코드]`(`파일:줄`) ·
`[문서]`(티켓 키·문서 링크) · `[추정]`. **이모지를 쓰지 않는다**(PDF 임베드가 불안정해 뷰어에
따라 두부로 나온다). 5·6장은 문장 옆 인라인, 나머지 장은 절 끝에 모아 쓴다.

**D4. 코드 식별자는 번역하지 않는다.** `UserService.create()` 는 그대로 둔다. 개념어만 한글을
앞세우고 첫 등장에 영문을 붙인다 — `이벤트 루프(event loop)`.

**D5. 지시문을 쓰지 않는다.** `~하세요`·`~하십시오`·`~시기 바랍니다` 가 나오면 설명서가
매뉴얼로 변질된 신호다. 절차는 링크로 넘긴다.
- 나쁨: `설정 화면에서 값을 바꾸세요.`
- 좋음: `설정은 <설정 화면>에서 바꾼다. 절차는 사용자 가이드에 있다.`

## 묶음 E — 사람이 쓴 글의 결 (산문 문서 공통)

A~D 가 **낱말과 문장**을 본다면 E 는 **문서의 결**을 본다. 낱말을 다 지켜도 읽기 힘든 글이 나온다.
실제로 한 판에서 A~D 를 전부 통과한 문서가 "AI 가 쓴 것 같아 읽기 힘들다"는 평을 받았다. 원인은
표가 절을 다 먹었고, 문장 길이가 균일했고, 독자에게 말을 거는 문장이 없어서였다.

적용 대상은 사람이 **읽는** 문서다 — 사용자 가이드, Confluence 산문, 문제 설명, 인수인계 핸드북.
개조식 문서(Jira 설명)와 기계가 소비하는 내부 구조 문서는 뺀다.

**E1. 표는 대조할 때만 쓴다.**
표는 여러 항목을 **같은 잣대로 견주는** 도구다. 항목마다 설명이 한 문장씩 들어가야 하면 그건 표가
아니라 문단이다. 한 절이 표로만 이루어져 있으면 거의 항상 잘못 고른 것이다.
- 나쁨: `| 항목 | 규약 | 어디에 구현 | 알려진 예외 |` 네 열에 각각 긴 문장 — 읽으려면 눈이 좌우로 계속 움직인다.
- 좋음: 중요한 두세 항목은 문단으로 풀어 쓰고, 나머지를 짧은 표로 모은다. 표 셀에는 이름·경로·숫자처럼 **눈으로 훑는 것**만 남긴다.

**E2. 문장 길이를 섞는다.**
비슷한 길이의 문장이 이어지면 기계가 쓴 티가 난다. 긴 문장 뒤에는 짧은 문장을 둔다. 특히 **중요한
사실은 짧게** 쓴다 — 짧은 문장이 눈에 걸린다.
- 나쁨: `셸은 파일에 손대지 않는다. 렌더러의 모든 바깥 접근은 서비스 계층을 거쳐 preload 다리를 지나 메인으로 넘어간다. 권한을 한곳으로 모으려는 것이고 그 덕에 화면 코드에는 Node API 가 한 줄도 없다.`
- 좋음: `셸은 파일에 손대지 않는다. 바깥으로 나가는 길은 하나뿐이다 — 서비스 계층에서 preload 다리를 지나 메인으로. 그래서 화면 코드에는 Node API 가 한 줄도 없다.`

**E3. 독자에게 말을 건다.**
읽는 사람이 지금 무엇을 해야 하는지, 무엇을 안 봐도 되는지 알려 준다. 지시문(D5)과 다르다 — 절차를
시키는 것이 아니라 **길을 알려 주는** 것이다.
- 좋음: `여기부터는 위키 기능을 손볼 때만 필요하다. 셸만 고칠 사람은 건너뛰어도 된다.`
- 좋음: `이 파일부터 열면 나머지가 따라온다.`

**E4. 무게를 준다.**
한 절에서 제일 중요한 사실을 첫 문장에 놓고, 사소한 것은 뒤에 묶는다. 전부 같은 무게로 나열하면
독자가 무엇이 중요한지 스스로 정해야 한다 — 그게 읽기 힘든 글의 정체다.

**E5. 항목이 셋 이하면 불릿 대신 문장으로 쓴다.**
불릿은 나열이지 설명이 아니다. 셋 이하는 문장으로 이으면 관계가 드러난다.

**E6. 절은 도입 한 문장으로 연다.**
제목 다음에 표나 그림이 바로 오면 독자가 무엇을 보는 중인지 모른다. 이 절이 무엇을 말하려는지 한
문장 쓰고 시작한다.
