# 참조: 크로스유닛 상호작용 & 액션→리액션 정합 (interaction-integrity)

> **왜 이 문서가 있나:** 유닛(페이지/리소스)을 격리해서 스펙·구현하면 각 유닛은 홀로는 맞지만 **유닛 사이의 연계**가 침묵 누락된다 — 페이지 A에서 수정한 게 페이지 B 목록에 반영 안 됨, 팔로우 토글이 다른 화면에 전파 안 됨 등. 이 문서는 그 크로스유닛 계약과 **사용자 액션 후 리액션(상태 정합)** 을 1급 산출/검증 대상으로 못박는다.
>
> 기획(스펙·플랜)은 이 문서를 읽어 **홀리스틱하게** 상호작용을 산출하고(→ `docs/specs/interactions.md`), 구현은 유닛 격리를 유지하되 이 계약을 소비한다. 리뷰는 이 계약이 실제로 배선됐는지 검증한다.

---

## A. 크로스유닛 상호작용 맵 (홀리스틱 기획이 산출 — `interactions.md`)

전 유닛을 한 컨텍스트에서 볼 때 아래를 명시적으로 산출한다(유닛별 스펙엔 안 잡히는 것):

1. **네비게이션 그래프** — 페이지↔페이지 전이, 진입점, **뒤로가기 시 어느 상태로 복귀**하는지. 각 전이는 출발 유닛 FR(Event-driven) + 도착 유닛 진입점 양쪽에 걸림.
2. **공유·크로스페이지 상태** — 여러 화면이 함께 읽는 상태(현재 유저·팔로우 여부·좋아요/카운트·장바구니 등). 어느 유닛이 소유(mutate)하고 어느 유닛이 구독(read)하는지 표로.
3. **크로스피처 결합** — 한 유닛 액션이 다른 유닛에 부수효과를 내는 경우(팔로우 토글 → 피드 구성·프로필 카운트 동시 변경). 강결합은 `plan.md`의 실행 순서·공유 배선으로 내림.
4. **BE 크로스리소스** — 리소스 간 FK/조인·**트랜잭션 경계가 여러 리소스를 걸치는 경우**(주문 생성 시 재고 차감)·cascade 삭제·이벤트 일관성. 스키마 공유(`prisma/schema.prisma`)로 인한 머지 순서.

## B. 액션 → 리액션 정합 체크리스트 (필수 — 조용한 누락 금지)

사용자 액션 뒤 **당연히 반영되어야 할 결과**를 유닛 경계를 넘어 못박는다. 각 mutation마다 "무엇이 어디에 반영되어야 하나"를 스펙 FR + plan 체크박스로 emit한다.

| 액션 | 반영되어야 하는 곳 (리액션) |
|---|---|
| **생성(Create)** | 관련 목록에 새 항목 등장(정렬 위치 포함), 카운트 증가 |
| **수정(Edit/Update)** | **그 항목이 나오는 모든 목록 + 상세 뷰에 갱신 반영** (수정 후 목록으로 나갔을 때 옛 값 금지) |
| **삭제(Delete)** | 목록에서 제거, 카운트 감소, 상세에 있었으면 안전한 경로로 이탈(redirect) |
| **토글(좋아요/팔로우 등)** | 그 상태를 보여주는 **모든 화면** 동기(낙관적 업데이트 시 실패 롤백) |
| **뒤로가기/재진입** | 캐시된 화면이 **신선한 데이터**를 보이도록(위 mutation 이후 stale 금지) |

추가로 항상 점검:
- **로딩/빈/에러 상태** — 액션 직후 pending·실패·빈 결과 UX가 정의됐는가.
- **경합/멱등** — 같은 액션 연타, 낙관적 업데이트 중 재요청.

### 추상화(기반) 영역도 예외 없음 — 액션→캐시/화면 상시 고려
인증·세션·권한처럼 **화면 뒤에 추상화된 기반 영역**도 그 자체가 액션의 원천이면 액션→리액션 정합을 **똑같이** 따진다(눈에 안 보인다고 빠뜨리기 쉬운 자리):
- **로그인 성공** → 인증 상태·현재 유저 캐시 갱신 + 유저 의존 화면(피드·프로필·헤더) 재조회/업데이트.
- **로그아웃** → **연계된 모든 캐시 초기화**(민감 데이터 잔존 금지) + 보호 라우트에서 이탈.
- **토큰 만료/갱신** → 진행 중 요청 재시도 또는 로그인 유도, stale 캐시 무효화.
- 일반화: **어떤 상태(state)를 바꾸는 액션이든 — 그 상태를 추상화해 숨겼더라도 — 연계 캐시 초기화 + 화면 업데이트를 항상 명시**한다. plan `[X]` 배선·reviewer 검증 대상.
> 이 영역은 소비 화면이 스펙에 없을 수 있다(예: 인증 API만 있고 로그인 화면 스펙 없음). 그 경우는 **먼저** `askquestion-principle.md`의 "짝 없는 능력(orphaned capability)" 예시대로 처리 방향을 사용자에게 확인한 뒤, 확정된 소비 방식에 위 정합을 건다.

## C. 배선 메커니즘 힌트 (plan/builder가 실제로 심는 것)

- **FE**: mutation 성공 시 의존 쿼리 **무효화(invalidate)/refetch** 또는 캐시 직접 갱신 — 중앙 `store/queries/keys.ts`의 queryKey를 공유해 A의 mutation이 B의 목록 key를 무효화하도록 배선. 낙관적 업데이트는 반드시 onError 롤백. 화면 재진입 신선도는 staleTime/refetchOnMount 정책으로.
- **BE**: 여러 리소스를 걸치는 쓰기는 **하나의 트랜잭션 경계**로. cascade/일관성은 스키마 관계 + 서비스 계층에서 보장. 목록 반영은 API 응답 계약(생성/수정 응답이 갱신된 표현 포함)으로.

## D. 역할별 사용

- **spec-author / bespec-author (홀리스틱)**: A의 상호작용 맵을 `interactions.md`로 산출 + B의 액션→리액션을 **각 유닛 requirements.md의 FR로도** emit(예: "게시글 수정 성공 시 피드 목록에 갱신 반영" = Event-driven FR). 미정 크로스유닛 결정은 `needsDecision`.
- **plan-author (홀리스틱)**: 유닛별 plan에 C의 배선을 **코드-레벨 체크박스**로 박음(예: `[ ] usePostEdit onSuccess → queryClient.invalidateQueries(['feed'])`). 크로스유닛 순서/공유 key를 plan에 고정.
- **fe-builder / be-builder (격리)**: `interactions.md` + 자기 plan을 읽어 위 배선을 구현. 공유 queryKey·트랜잭션 경계를 스펙/plan대로 준수(임의 결정 금지 — 미정이면 needsDecision).
- **reviewer**: `interactions.md`의 액션→리액션 항목이 **실제로 배선됐는지** 검증 — mutation에 대응하는 invalidate/refetch/캐시갱신(FE)·트랜잭션 경계(BE)가 없으면 `NEEDS_REPAIR`(rule: `interaction-integrity`).
