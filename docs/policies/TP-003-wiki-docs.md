# TP-003 위키 문서는 7종 템플릿과 공통 머리로 쓰고, 정해진 페이지 트리에 둔다

## 맥락

`dt-confluence-doc`의 상태는 다음과 같았다.

- 문서 종류가 4개로 고정돼 있었다. 회의록, 작업 요약, 기술 문서, 회고·릴리즈노트다.
  - 기술 문서 하나에 설계·위키·사용법이 섞였다.
  - 회고와 릴리즈노트는 한 종류 안에서 모드로 갈렸다.
- 문서마다 담당자·상태·다시 볼 날짜가 없어, 누가 맞는지 확인할 문서인지 알 수 없었다.
- 페이지를 둘 곳이 부모 하나뿐이라 모든 문서가 한곳에 쌓였다.
- Confluence 전용이었다.

로드맵 GEN-10(DEV-15)을 하면서 문서 표준을 리서치해 새로 정했다. 참고한 것은 Diátaxis 문서 체계, Confluence 구조 권장, Google 설계 문서와 SRE 장애 회고, 문서 신선도 관리다. 작업 기록 규칙(TP-002)과 같은 방식이다.

## 결정

**위키 문서는 7종 템플릿으로 쓰고, 모든 문서 맨 위에 공통 머리(상태·담당자·관련 이슈·관련 결정·요약)를 둔다. 페이지는 종류별 구역 아래 정해진 제목 규칙으로 둔다.**

### 1. 문서 종류

| 종류 (`type`) | 목적 | 구성 |
|---|---|---|
| 회의록 `meeting` | 기록 | 목적·참석자 → 안건 → 논의 → 결정 사항 → 액션 아이템 |
| 작업 보고 `report` | 기록 | 요약 → 완료·진행·예정 표(이슈 키) → 이슈·위험 → 다음 계획 |
| 설계 문서 `design` | 설명 | 배경 → 목표·범위 밖 → 제안 → 검토한 대안과 트레이드오프 → 위험·미결 → 결정 |
| 운영 가이드 `guide` | 하우투 | 언제 쓰나 → 준비물 → 절차(번호) → 확인 방법 → 문제가 생기면 |
| 회고 `retro` | 기록 | 기간·참여자 → 잘된 점·바꿀 점 → 액션 아이템 |
| 릴리즈 노트 `release` | 레퍼런스 | 버전·날짜 → 변경 표(추가·고침·변경, 이슈 키) → 배포·확인 사항 |
| 장애 회고 `postmortem` | 기록 | 요약 → 영향 → 타임라인 → 원인(기여 요인) → 액션 아이템 |

- 한 문서에는 한 종류만 쓴다. 설계와 사용법이 다 필요하면 설계 문서와 운영 가이드 두 개로 나누고 서로 링크한다.
- 장애 회고는 **누구를 탓하지 않고** 쓴다. 사람이 아니라 조건과 절차를 원인으로 적는다. 사실(타임라인)을 분석보다 먼저 둔다.
- 튜토리얼과 API·설정 레퍼런스는 이 목록에 없다. 코드 저장소의 문서, `/dt-handbook`·`/dt-guide`가 맡는다.
- 오래 갈 결정의 원본은 저장소의 결정 문서(PD·TP — `/dt-decision`)다. 위키 문서에는 링크만 두고 내용을 다시 쓰지 않는다.

### 2. 공통 머리

모든 문서 맨 위에 둔다.

```
상태: {초안 | 검토 중 | 확정 | 폐기}   담당자: {@이름}   검토일: {YYYY-MM-DD} (다음 검토: {YYYY-MM-DD})
관련 이슈: {이슈 키들}   관련 결정: {PD·TP 번호}
요약: {이 문서가 무엇이고 무엇을 정했는지 2~3줄}
```

- **담당자**는 내용이 맞는지 책임지는 사람이다. 기본은 작성자다.
- **검토일**은 설계 문서와 운영 가이드에만 둔다. 다음 검토는 기본 6개월 뒤다. 그 시점의 기록인 문서는 낡지 않으므로 검토일을 두지 않는다. 회의록·작업 보고·회고·릴리즈 노트·장애 회고가 그렇다.
- 검토일은 수정한 날이 아니라 **사람이 내용을 확인한 날**이다. 관련 코드나 설계가 크게 바뀌면 다음 검토일 전이라도 다시 본다.
- "폐기"로 바꿀 때는 대체 문서 링크를 남긴다.
- 값이 없는 칸은 줄째 뺀다. 관련 결정이 없으면 그 칸을 쓰지 않는다.

### 3. 페이지 트리와 제목

```
(스페이스 홈) 프로젝트 개요 — 하위 페이지 목록, 최근 문서
 ├ 설계            [설계] {기능명}
 ├ 운영 가이드     [가이드] {할 일}
 ├ 회의록          {YYYY-MM-DD} {회의 주제}          ← 연도별 하위 페이지
 ├ 보고·회고       {YYYY-MM-DD} {기간} 작업 보고 / {YYYY-MM-DD} {기간} 회고
 ├ 릴리즈 노트     {버전} 릴리즈 노트
 └ 장애 회고       {YYYY-MM-DD} 장애: {한 줄 요약}
```

- 최상위 구역은 여섯 개다. 팀이 더할 수는 있지만 여덟 개를 넘기지 않는다.
- 시간순으로 쌓이는 문서는 날짜를 제목 앞에 둔다. 그래야 트리에서 정렬된다.
- 종류마다 라벨을 붙인다: `doc-meeting` · `doc-report` · `doc-design` · `doc-guide` · `doc-retro` · `doc-release` · `doc-postmortem`.
- 종류의 구역 페이지가 없으면 스킬이 "이 구역 페이지를 만들까요?"를 묻고, 승인을 받아 만든다.

### 4. 트래커와 연결

- **문서 → 이슈**: 공통 머리의 "관련 이슈"에 이슈 키를 적는다.
- **이슈 → 문서**: 관련 이슈의 **웹 링크** 칸에 문서를 단다(제목 = 문서 제목, 요약 = `{종류} · {작성일}`). 같은 주소가 이미 있으면 다시 달지 않는다. 트래커가 웹 링크를 받지 않으면 `📄 관련 문서: [{문서 제목}]({URL}) ({종류} · {작성일})` 댓글로 대신한다 — 형식은 TP-002의 "관련 문서" 줄과 같다. 작업 기록(`/dt-worklog`)도 이 문서를 찾아 그 줄에 넣는다.
- **액션 아이템**(회의록·회고·장애 회고): 원하면 `/dt-worklog`로 TP-002의 Task로 등록하고, 문서에는 그 이슈 키를 적는다. 액션을 추적하는 원본은 트래커다.

### 5. 위키 종류

`.dt.json`의 `wiki`로 고른다.

- `confluence`(기본): Confluence에 쓴다.
- `markdown`: 같은 템플릿으로 저장소의 `docs/wiki/`에 쓴다.
- `notion`: 아직 연동하지 않는다. `none`처럼 동작한다.
- `none`: 본문을 대화에 마크다운으로 보여 주고 끝난다.

템플릿은 하나만 두고, 위키 종류에 맞게 바꿔 쓴다(Confluence는 HTML).

## 이유

- **종류를 목적별로 나눈다.** Diátaxis는 배우기·일하기·찾아보기·이해하기를 한 문서에 섞으면 어느 쪽 독자에게도 읽기 어렵다고 본다. 예전 "기술 문서"가 설계·사용법·위키를 한데 담아 그랬다.
- **공통 머리를 둔다.** 담당자가 없는 문서는 아무도 고치지 않아 낡는다. 수정 시각이 아니라 사람이 확인한 날을 남겨야 낡았는지 판단할 수 있다(신선도 관리 리서치). 처음에는 담당자와 검토일 두 가지로 시작하라는 권고를 따라, 검토일은 낡을 수 있는 문서에만 둔다.
- **트리를 얕고 일정하게 한다.** 최상위를 적게, 주제별로 얕게, 공통 분류는 라벨로 두는 것이 Confluence 운영의 일반적인 권장이다. 프로젝트마다 같은 구역을 두면 처음 온 사람도 찾는다.
- **장애 회고를 따로 둔다.** 탓하지 않는 형식과 사실 우선 순서(Google SRE)는 일반 회고와 목적이 다르다. 액션 아이템을 트래커에서 추적해야 재발 방지가 실제로 된다.
- **결정과 액션의 원본은 각자의 자리에 둔다.** 결정은 저장소 PD·TP, 액션은 트래커가 원본이다. 위키에 다시 쓰면 두 곳이 어긋난다.

## 버린 대안

- **예전 4종 유지**: 기술 문서 하나가 설계·사용법을 다 담아 독자가 갈리고, 장애 회고 자리가 없다.
- **Diátaxis 4종 그대로**: 회의록·보고·회고 같은 팀 기록 문서가 들어갈 자리가 없다. 기술 문서 쪽 원리만 가져왔다.
- **모든 문서에 검토일**: 회의록처럼 그 시점의 기록은 낡지 않는데, 검토 요청만 쌓인다.
- **구역 페이지를 사람만 만들기**: 처음 쓰는 팀은 매번 막힌다. 묻고 만드는 쪽이 낫다.
- **결정 내용을 위키에도 쓰기**: 저장소 PD와 위키가 어긋난다. 링크만 둔다.
