# TP-002 작업 기록은 Story·Task·Bug 단위로, 설명·진행·마무리 템플릿으로 남긴다

## 맥락

`dt-worklog-sync`는 한 회사의 Jira 가이드라인을 모든 사용자에게 강제했다. 그 규칙은 다음과 같다.

- 기록 단위는 반드시 Sub-task, 크기는 1~3일.
- 부모는 "수행" Epic 아래에 두고, 시작일·종료일을 필수로 받는다.
- Story는 파트별 상태로 움직인다.
- "산출물" 커스텀 필드가 없으면 Done을 막는다.
- 커밋 주소는 GitLab 형식으로만 만든다.

다른 조직의 Jira·GitHub·Linear에는 맞지 않았다. 로드맵 GEN-09(DEV-14)를 하면서, 그 가이드라인 대신 일반 프로젝트에 맞는 기록 규칙을 새로 정했다.

## 결정

**기록의 기본 단위는 Story·Task·Bug이고, 설명 1종과 댓글 2종(진행·마무리) 템플릿으로 남긴다. Done 직전에는 산출물이나 결정 사항이 든 마무리 댓글이 꼭 있어야 한다.**

### 1. 계층

```
Epic        결과 하나(몇 주~분기). 측정할 수 있는 목표 한 줄
 ├ Story    사용자에게 보이는 기능 하나            ┐
 ├ Task     기술·운영 작업(설계·인프라·리팩터·배포) ├ 같은 층 — 기록의 기본 단위
 └ Bug      결함 하나                              ┘
     └ Sub-task  (선택) 한 이슈를 여러 사람이 나눠 할 때만
```

- **기본 단위는 Story·Task·Bug다.** 담당자 한 명이 대략 **한 주 안에** 끝낼 크기로 잡는다. 더 크면 나누거나 Epic으로 올린다.
- **Story와 Task를 가르는 기준**은 사용자에게 보이는지다. 화면이나 API처럼 사용자에게 보이는 기능은 Story, 그렇지 않은 기술·운영 작업은 Task다.
- **Sub-task는 강제하지 않는다.** 한 이슈를 여러 사람이 나눠 할 때만 쓴다. 혼자 하는 단계는 설명의 완료 조건 체크박스로 충분하다.
- **Epic이 있으면 그 아래에 둔다.** 없어도 기록할 수 있다. 스킬은 Epic을 새로 만들지 않고 고르게만 한다.
- **사소한 변경은 이슈로 만들지 않는다.** 관련 이슈에 진행 댓글로 남긴다.
- **의존 관계는 계층이 아니라 링크로 표시한다**(blocks · relates to).
- **날짜와 추정은 필수가 아니다.** 팀이 원하면 프리셋으로 켠다.

트래커별로 같은 자리는 아래와 같다.

| | Jira | GitHub | Linear |
|---|---|---|---|
| 결과 묶음 | Epic | Milestone 또는 부모 이슈 | Project |
| 기본 단위 | Story · Task · Bug | Issue(종류는 라벨) | Issue |
| 나눈 일 | Sub-task | Sub-issue | Sub-issue |

### 2. 설명 템플릿 (이슈를 만들 때)

"어떻게"는 설명에 넣지 않는다. 설명은 문제와 완료 조건만 담고, 진행 과정은 댓글로 남긴다.

```markdown
## 배경
{왜 하는가 — 문제나 요청. 요청이면 출처 한 줄}

## 목표
{무엇이 되면 끝인가 — 1~2문장}
- 범위 밖: {이번에 하지 않는 것}   ← 있을 때만

## 완료 조건
- [ ] {확인할 수 있는 조건}

## 참고
- {스펙·디자인·관련 이슈·관련 문서 링크}
```

Bug는 "목표" 자리에 **재현 절차 · 기대 결과 · 실제 결과 · 환경**을 쓴다.

### 3. 댓글 템플릿

**진행 댓글**은 작업 중 언제든, 상태를 바꿀 때 남긴다.

```markdown
**진행** — {진행 중 | 막힘 | 검토 대기}
- 한 일: {이번에 한 것}
- 다음: {다음에 할 것}
- 막힌 것: {누구의 무엇이 필요한지}   ← 있을 때만
- 산출물: {PR·커밋·문서 링크}         ← 있을 때만
- 관련 문서: {문서 링크}              ← 있을 때만
```

**마무리 댓글**은 Done 직전에 꼭 하나 남긴다.

```markdown
**완료**
- 결과: {무엇이 바뀌었나 — 1~2문장}
- 산출물: {PR/커밋, 문서, 배포 URL, 테스트 결과}
- 결정 사항: {무엇을 왜 정했나, 버린 대안}   ← 오래 갈 결정이면 PD 문서 링크
- 완료 조건: {설명의 체크박스 n/n — 못 채운 것은 이유}
- 관련 문서: {문서 링크}                     ← 있을 때만
- 남은 일: {후속 이슈 키}                     ← 있을 때만
```

**관련 문서**는 이번 작업과 관련된 위키 문서(Confluence 등)가 이미 있으면 그 링크다. 스킬이 찾아서 제안하고, 사람이 고른 것만 넣는다. 형식은 문서 스킬의 역링크와 같다: `📄 [{문서 제목}]({URL}) ({종류} · {작성일})`. 이슈에 이미 있는 링크는 다시 넣지 않는다.

### 4. 마무리 규칙

1. Done 전에 마무리 댓글이 있어야 한다.
2. 마무리 댓글에는 **산출물이나 결정 사항이 적어도 하나** 있어야 한다.
   - 조사나 설계 검토처럼 결정만 남는 일도 완료다.
   - 둘 다 없으면 Done을 막고 사람에게 묻는다.
3. 설명의 완료 조건 체크박스를 갱신한다. 못 채운 항목은 이유를 적는다.
4. 산출물은 **댓글 본문**에 둔다. 어느 트래커에서나 되는 방식이다. 커스텀 필드(예: "산출물")는 팀 프리셋이 켰을 때만 추가로 채운다.

### 5. 조직 규칙은 프리셋으로

- 이 정책이 기본 프리셋 `basic`이다.
- 조직마다 다른 규칙은 선택 프리셋으로 둔다. 예: Sub-task 강제, 크기 1~3일, 필수 커스텀 필드, 필수 날짜, 파트별 상태, Bug 단계별 댓글.
- 앞의 회사 가이드라인은 `org-guideline` 프리셋으로 남긴다. 고른 팀만 그 규칙을 쓴다.

## 이유

- **Story·Task·Bug를 같은 층에 둔다.** Jira 기본 계층과 커뮤니티의 흔한 합의가 같은 층이다. Linear·GitHub의 기본 단위(Issue)와도 한 자리로 대응되어, 트래커를 바꿔도 규칙이 같다.
- **Sub-task를 강제하지 않는다.** 강제하면 혼자 하는 일도 부모 이슈를 먼저 찾거나 만들어야 한다. 그 사이에 기록이 끊긴다. Atlassian도 Sub-task 단위로는 추정하지 말라고 권한다.
- **"어떻게"를 설명에서 뺀다.** 설명에는 문제와 완료 조건을 둔다. 해결 방법은 일하면서 바뀌므로 댓글에 남는 편이 사실과 맞는다(Linear 방식).
- **마무리에 결정 사항도 인정한다.** 코드 없이 끝나는 조사·설계 일이 산출물 링크가 없다는 이유로 Done을 못 하는 일이 있었다. 결정을 남기는 것이 그 일의 산출물이다.
- **완료 조건과 팀 완료 기준을 나눈다.** 이슈의 완료 조건은 이슈마다 다르고, 팀의 완료 기준(DoD)은 모든 이슈에 같다. 이 정책의 마무리 규칙이 팀 완료 기준이고, 설명의 체크박스가 이슈의 완료 조건이다.

## 버린 대안

- **Sub-task를 기본 단위로(앞의 회사 규칙)**: 혼자 하는 일에도 부모가 필요해 기록이 무거워진다. 다른 트래커와 대응도 어긋난다. `org-guideline` 프리셋으로만 남긴다.
- **Story 없이 Task 하나로**: 더 단순하다. 하지만 사용자에게 보이는 기능과 기술 작업을 나눠 보는 보고(릴리즈 노트·기능 진척)가 어렵다. 라벨로 대신하면 팀마다 라벨이 갈린다.
- **크기 1~3일**: 하루 단위 작업은 기록 횟수가 늘고, 이슈가 할 일 목록처럼 잘게 쪼개진다. 한 주 안을 기준으로 두고, 더 잘게 나누고 싶은 팀은 프리셋으로 정한다.
- **산출물만 Done 조건으로(앞의 규칙)**: 조사·설계 일이 막힌다. 결정 사항도 인정한다.
- **산출물을 커스텀 필드에만**: 필드 이름과 형식이 Jira 인스턴스마다 다르다. GitHub·Linear에는 그런 필드가 없다. 댓글 본문이 공통 자리다.
