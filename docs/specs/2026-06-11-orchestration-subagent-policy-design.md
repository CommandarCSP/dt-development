# 오케스트레이션 서브에이전트 정책 설계 문서

- 작성일: 2026-06-11
- 상태: 설계 확정 (구현 보류 — 전체 스킬 정비 후 일괄 진행)
- 대상 플러그인: `dt-development`

## 1. 목적

dt-development의 오케스트레이터 스킬들이 여러 작업을 진행할 때 **서브에이전트로 컨텍스트를 격리해 병렬 처리**하는 것을 기본으로 한다. 단, 특정 작업에서 병렬이 오히려 불리하면 **사용자가 순차를 선택**할 수 있게 한다. 리뷰를 담당하는 작업은 **항상 서브에이전트로 격리**한다(에이전트가 지원하는 한 예외 없음).

> 동기: 현재 코드 생성(scaffold Phase 2)·소스 분석(dt-spec/dt-bespec)은 서브에이전트로 격리돼 있으나, **리뷰/repair 판단이 오케스트레이터 메인 컨텍스트에서 인라인 실행**(scaffold "Final review & repair — 메인이 직접 수정")되어 컨텍스트가 오염된다. 또한 병렬/순차 결정이 체크리스트에 하드코딩되어 사용자가 개입할 수 없다.

## 2. 단일 출처(SSOT)

신설: **`plugin/docs/orchestration-policy.md`** — 아래 4원칙을 정의하는 공용 정책 문서. 모든 오케스트레이터 스킬이 이 문서를 참조한다(규칙을 각 SKILL.md에 중복 기재하지 않음).

## 3. 정책 4원칙

### 원칙 1 — 병렬 기본 + 자동 추천 + 시작 시 1회 확인
- 오케스트레이터는 작업 단위의 **의존성을 분석**해 실행 모드를 추천한다:
  - **독립(disjoint owner — 서로 다른 파일/경로만 수정, 공유 상태 없음)** → 병렬 추천
  - **강결합(공유 의존, 한 단위가 다른 단위 산출물을 입력으로 필요)** → 순차 추천
- 오케스트레이션 시작 시 **AskUserQuestion 1회**: `병렬(추천) / 순차 / 자동(추천대로)`. 사용자가 확정하며 추천을 override할 수 있다.
- **기본값 = 병렬.** 사용자가 답을 생략/자동 선택하면 추천 모드로 진행.
- 추천 근거(예: "5단위 중 4개 독립 → 병렬")를 함께 제시한다.

### 원칙 2 — 순차 = 직렬 서브에이전트 (격리 유지)
- 사용자가 순차를 선택해도 **각 작업 단위를 서브에이전트로 격리**해 **한 번에 하나씩** dispatch한다(병렬성만 끈다).
- 비격리 메인 인라인 처리 금지(사소한 단일 편집 제외). 컨텍스트 격리는 병렬/순차와 무관하게 유지.
- 참고 패턴: superpowers `subagent-driven-development`(작업당 fresh 서브에이전트 + 단계별 리뷰).

### 원칙 3 — 리뷰는 항상 격리 (불변, 선택 무관)
- **모든 리뷰 작업을 전용 review 서브에이전트에서 수행한다.** 범위: `review.mjs` 실행 + diff 읽기 + 위반 해석 + repair 필요 판단.
- 메인(오케스트레이터)은 **verdict만 반환받는다**(예: `Critical N건, 위반 파일 목록, repair 지시`). diff·추론은 review 서브에이전트 컨텍스트에 격리.
- **repair는 담당 코드 서브에이전트 재dispatch**로 수행한다. 기존 scaffold의 "메인이 직접 수정" 경로는 제거.
- 이 원칙은 **병렬/순차 사용자 선택과 무관하게 항상** 적용된다(사용자가 끌 수 없음).
- 적용: `/dt-review`·`/dt-be-review` 단독 실행 시에도, 더 큰 오케스트레이션(scaffold 등) 안에서 호출될 때도 동일.

### 원칙 4 — 에이전트 미지원 시 폴백
- 런타임이 서브에이전트(Task/Agent)를 제공하지 않으면 인라인 실행으로 degrade한다. ("에이전트가 지원하는 한"이라는 단서.)
- 폴백 시 그 사실을 사용자에게 1줄로 알린다(격리가 적용되지 않음을 명시).

## 4. 적용 대상 (참조처)

| 스킬 | 변경 |
|---|---|
| `dt-frontend-scaffold` / `dt-backend-scaffold` | Phase 2 병렬 dispatch는 유지 + **시작 시 병렬/순차 선택(원칙 1) 추가**. 미니/풀 리뷰·repair를 **review 서브에이전트로 이동(원칙 3)** — "메인 직접 수정" 제거 |
| `dt-spec-generate` / `dt-bespec-generate` | 소스 어댑터 병렬 분석에 **시작 시 선택(원칙 1) 추가** |
| `dt-implement` / `dt-be-implement` | scaffold 위임으로 정책 상속. 다중 도메인 "범위" 질문과 별개로 병렬/순차 선택 노출 |
| `dt-frontend-review` / `dt-backend-review` | SKILL.md에 **"오케스트레이션 내 호출 시 항상 서브에이전트 격리(원칙 3)"** 명시. 스크립트(`review.mjs`) 자체는 변경 없음 — 호출을 감싸는 격리만 추가 |

## 5. 참고 패턴 (superpowers)
- **병렬**: `dispatching-parallel-agents` — 2개 이상 독립 작업 동시 dispatch.
- **순차 + 리뷰**: `subagent-driven-development` — 작업당 fresh 서브에이전트, 2단계(스펙/품질) 리뷰. 본 정책의 순차·리뷰 격리 모델의 기준.

## 6. 비범위 / 주의
- 본 문서는 **요구사항·정책 설계**다. 실제 구현(orchestration-policy.md 작성 + 각 스킬 패치 + review-agent 프롬프트 신설)은 **전체 스킬 정비 완료 후 개선사항 일괄 진행 시점**에 한다.
- 의존성 분석은 휴리스틱(파일 owner 중첩/공유 import 여부)로 충분 — 정적 그래프 분석까지 가지 않는다(YAGNI).
- 리뷰의 기계적 검출(`review.mjs`)은 결정적 스크립트이므로 로직 변경 없음 — 오직 "어느 컨텍스트에서 실행/해석하느냐"만 바꾼다.

## 7. 성공 기준 (구현 시 검증할 것)
- [ ] 오케스트레이터 시작 시 병렬/순차 선택이 1회 제시되고 override 가능, 기본 병렬.
- [ ] 순차 선택 시에도 각 단위가 서브에이전트로 격리 실행됨.
- [ ] 리뷰/repair가 메인 컨텍스트에 diff/추론을 남기지 않음(verdict만) — 병렬/순차 무관.
- [ ] repair가 담당 코드 서브에이전트 재dispatch로만 일어남(메인 직접 수정 없음).
- [ ] 서브에이전트 미지원 환경에서 인라인 폴백 + 사용자 고지.
- [ ] 정책이 SSOT 1곳에 정의되고 오케스트레이터들이 참조(중복 없음).
