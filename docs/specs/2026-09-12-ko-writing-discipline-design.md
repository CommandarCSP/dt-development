# 한글 작성 규율 강화 — 의인화·번역투·낯선 용어 제거 + 리뷰 1회 필수 설계 문서

- 작성일: 2026-09-12
- 상태: 설계 확정 (사용자 승인 2026-09-12)
- 범위: `docs/refs/readable-writing.md` 개정 · 외부 분류 벤더링 · 기계 사전 검사 스크립트 · 격리 리뷰 에이전트 · 소비 스킬 연결(계층 1: 산문 3개 스킬은 리뷰어, 계층 2: 내부 구조 문서 author 에이전트 4개 + E2E 스킬 2개는 lint)
- 대상 플러그인: `dt-development` (`plugin/`)
- 후속: 사용자 가이드 PDF 생성 스킬(별도 스펙 예정)이 이 문서의 리뷰 에이전트를 그대로 쓴다

## 1. 목적

플러그인이 만드는 한글 산출물(Jira 설명·코멘트, Confluence 문서, 문제 설명 답변, 앞으로의 사용자 가이드)에서
**AI가 쓴 티와 번역 티를 없앤다.** 지금 `readable-writing.md`는 이해 장벽(묶음 A)과 문장 다듬기(묶음 B)만 다루어,
다음 세 가지를 잡지 못한다.

| 못 잡는 것 | 실제 예 (AcmeNotes 사용자 가이드 0.3.3 본문) |
|---|---|
| 의인화 — 기계에 사람 행위를 붙임 | `트레이가 알려 줍니다`, `앱이 필요한 것을 이미 품고 있습니다` |
| 번역투 — 영어 구문 직역 | `설정에 의해 결정됩니다`, `가장 중요한 기능 중 하나` |
| 낯선 용어 — 일상에서 안 쓰는 한자어 | `설치 수행 후 재시작이 요구됩니다` |

또 지금은 "체크리스트로 점검한다"가 **작성자 자신의 자가 점검**이라 같은 글에서 잡히는 항목이 매번 다르고,
빠뜨려도 드러나지 않는다. 이 문서는 규칙을 보강하고, 점검을 **격리 리뷰 1회 필수**로 바꾼다.

## 4. 규칙 SOT 개정 — `docs/refs/readable-writing.md`

기존 대원칙·묶음 A(A1~A3)·묶음 B(B1~B4)는 그대로 둔다. 아래를 더한다.

### 4-1. 묶음 C — 우리말답게 (AI·번역 티 제거)

**C1. 기계에 사람 행위를 붙이지 않는다 (의인화).**
무생물 주어(앱·화면·버튼·트레이·설정·서버·기능)에 **사고·감정·의사소통 동사**를 붙이지 않는다.
기계 동작을 서술하는 동사는 허용한다.

| 금지 동사 (예) | 허용 동사 (예) |
|---|---|
| 알려 주다, 말하다, 안내하다(사람 화자일 때만 허용), 기억하다, 이해하다, 판단하다, 원하다, 기대하다, 도와주다, 챙기다, 품다, 고민하다, 신경 쓰다, 노력하다 | 표시하다, 보여 주다(화면이 그림을), 저장하다, 열다/닫다, 실행하다, 보내다/받다, 만들다, 지우다, 바꾸다, 확인하다(검사 의미), 처리하다 |

- 나쁨: `작업이 멈춘 것인지 트레이가 알려 줍니다.`
- 좋음: `작업이 멈추면 트레이에 그 상태가 표시됩니다.`
- 나쁨: `앱이 필요한 것을 이미 품고 있습니다.`
- 좋음: `필요한 구성 요소는 앱에 이미 들어 있습니다.`

경계 판단: "이 동사를 사람이 아닌 기계가 한다고 말해도 이상하지 않은가"를 묻는다. 이상하면 C1 위반이다.

**C2. 영어 구문을 직역한 티를 지운다 (번역투).**

| 패턴 | 나쁨 | 좋음 |
|---|---|---|
| `~에 의해` 피동 | 설정에 의해 결정됩니다 | 설정이 정합니다 |
| `~을/를 통해` 경로 도식 | 설정 화면을 통해 바꿀 수 있습니다 | 설정 화면에서 바꿀 수 있습니다 |
| `~에 있어(서)` | 사용에 있어 주의할 점 | 쓸 때 주의할 점 |
| `~에 대해/대한` 남용 | 오류에 대해 확인합니다 | 오류를 확인합니다 |
| 이중 피동 `~되어지다/보여지다` | 저장되어집니다 | 저장됩니다 |
| `~중 하나` (one of) | 가장 중요한 기능 중 하나입니다 | 특히 중요한 기능입니다 |
| 직역 대명사 `그것/그들/이것은` | 그것은 다음 질문부터 적용됩니다 | 다음 질문부터 적용됩니다 |
| 무생물 복수 `-들` | 파일들을 넣으면 | 파일을 넣으면 |
| `~을 가지다` (have) | 두 가지 방식을 가집니다 | 두 가지 방식이 있습니다 |
| `~로 인한/인해` | 오류로 인해 멈춥니다 | 오류 때문에 멈춥니다 |

`~을 통해`·`~에 대해`는 실제 경로·대상을 뜻할 때는 자연스럽다("네트워크를 통해 전송"). 리뷰어는 **대체어로 바꿔도 뜻이 같으면** 위반으로 본다.

**C3. 평소에 안 쓰는 말을 쓰지 않는다 (낯선 용어).**
일상어가 있으면 일상어를 쓴다. 시작 치환표(문맥에 따라 예외 가능 — 리뷰어가 확인):

| 낯선 말 | 일상어 |
|---|---|
| 수행하다 | 하다 |
| 존재하다 | 있다 |
| 해당 (명사 앞) | 그, 이 |
| 확보하다 | 마련하다, 갖추다 |
| 소요되다 | 걸리다 |
| 발생하다 | 생기다, 나다 |
| 완료되다 | 끝나다 |
| 요구되다 | 필요하다 |
| 활용하다 | 쓰다 |
| 위치하다 | 있다 |
| 진행하다 (단독) | 하다 |
| 기인하다 | ~ 때문이다 |
| 도출하다 | 얻다, 뽑다 |
| 제공하다 (사외 문서) | 주다, 있다(기능이 있다) |
| 선택 가능하다 | 고를 수 있다 |

사외 독자용 문서(사용자 가이드)에서는 개발 용어(빌드·배포·인스턴스·캐시·토큰)를 **첫 등장에서 풀어 쓰거나** 일상어로 바꾼다. 내부 문서(Jira·Confluence)에서는 A1·A2가 이미 다룬다.

**C4. AI가 쓴 글의 버릇을 지운다.**
yoonmoon AI 티 11종 중 우리 산출물에서 실제로 나오는 것만 뽑았다.

| 버릇 | 나쁨 | 좋음 |
|---|---|---|
| 상투 도입구 | 결론적으로 / 주목할 점은 / 흥미롭게도 | (지우고 본론으로) |
| 문두 접속사 반복 | 또한 ~. 따라서 ~. 또한 ~. | 흐름으로 잇고 접속사는 꼭 필요한 곳 한 번 |
| 형식명사 종결 | 확인하는 것이 중요합니다 | 확인해야 합니다 |
| 강조 부사 남발 | 매우 중요하고 정말 유용합니다 | 중요합니다 |
| `-적` 연쇄 | 기술적 토대의 구조적 측면 | 기술 기반의 구조 |
| 영어 병기 과다 | 프레임워크(framework)를 (매번) | 첫 등장만 병기, 이후 한국어 |
| 균일한 리듬 | 모든 문장이 같은 길이·같은 종결 | 짧은 문장과 긴 문장을 섞음 |
| 홍보 어휘 | 강력한 / 혁신적인 / 놀라운 | 구체적 사실로 |

### 4-2. B1 확장 — 독자별 문체 표

기존 B1의 두 줄(Jira 개조식 / Confluence 정중체)을 표로 바꾸고 한 행을 더한다.

| 문서 | 독자 | 문체 | 추가 규율 |
|---|---|---|---|
| Jira 설명·코멘트 | 팀 내부 | 개조식(명사·서술 종결) | 다만 C4 "과소 서술"은 피한다 — 성분·조사를 뭉개지 않는다 |
| Confluence 산문 | 팀·조직 내부 | "~합니다" 정중체 | — |
| 문제 설명 답변(dt-explain) | 요청자 | "~합니다" 정중체 | 근거 라벨(🟢/🟡)은 answer-frame이 정한다 |
| **사외 사용자 가이드** | 제품을 처음 보는 일반 사용자 | "~합니다" 정중체 + 쉬운 말 | 2인칭('여러분'·'당신'·'사용자님') 회피 — 필요하면 주어 생략. 개발 용어 첫 등장 풀이 필수(C3). 사내 시스템·티켓 키 언급 금지(사외 공개) |
| **내부 구조 문서** (requirements·design·api-contract·definition·E2E 시나리오 원장·plan) | 같은 팀 개발자 | 평서체("~한다") — 기존 산출물과 같게 | **한글 서술에** 묶음 B·C 적용: 페이지 목적, 사용자 스토리, Given-When-Then 서술, 결정 근거, 그리고 **EARS 줄의 한글 부분**(`THE SYSTEM SHALL 해당 항목을 …`의 서술 — 스펙에서 사람이 읽는 본문의 대부분이 여기다). **검사 대상 아님**: EARS 키워드 자체(`WHEN`·`WHILE`·`WHERE`·`IF`·`THEN`·`THE SYSTEM SHALL` — 마스킹; `IF-8` 같은 인터페이스 id는 키워드가 아님), UI 요소·엔드포인트 목록 줄(`` `id` (role) — … ``), 출처·패턴 라벨(`[ai-confirmed]` 등), 주석만 있는 줄(`<!-- … -->`). 게이트는 lint만(D8) |

### 4-3. 보존 원칙 (리뷰·수정 공통)

고치는 쪽이 지켜야 할 불변:
- 고유명사, 수치·단위·날짜, 코드 식별자·명령어·파일 경로, 인용문은 한 글자도 바꾸지 않는다.
- 주장의 방향과 강도를 바꾸지 않는다("항상"을 "대개"로 바꾸지 않는다).
- 격식체 수준을 바꾸지 않는다(정중체 → 평서체 금지).
- **과교정 가드(D7)**: 한 문단에서 바뀐 문장이 절반을 넘으면 그 문단은 고치지 않고 `확인 요망`으로 표시해 사람에게 넘긴다.

### 4-4. 체크리스트 갱신

기존 7항(A1~A3, B1~B4) 뒤에 추가:
- [ ] (C1) 무생물 주어에 사고·감정·의사소통 동사가 붙지 않았는가
- [ ] (C2) `~에 의해`·`~을 통해`·이중 피동·`~중 하나`·직역 대명사·무생물 복수가 없는가

- [ ] (보존) 고유명사·수치·코드·주장 강도가 그대로인가

문서 하단에 벤더 분류 참조를 적는다: "판정이 애매하면 `${CLAUDE_PLUGIN_ROOT}/rules/vendored/yoonmoon/`의 분류 원문(번역투 8종·AI 티 11종)을 근거로 삼는다."

## 6. 기계 사전 검사 — `scripts/koWritingLint.mjs`

### 6-1. 책임
텍스트를 받아 **확실한 패턴만** 정규식으로 짚어 findings를 돌려준다. 판정·수정은 하지 않는다(D6).
기존 스크립트 규약(`scripts/*.mjs`, ESM, 순수 함수 export + CLI 진입)을 따른다.

### 6-2. 검출 규칙

| id | rule | 패턴 (요지) | hint |
|---|---|---|---|
| L-C2-passive | C2 | `에 의해`, `에 의한` | 주어를 살려 능동으로 |
| L-C2-through | C2 | `을 통해`, `를 통해`, `을 통한`, `를 통한` | `에서`/`으로`로 바꿔도 뜻이 같은지 확인 |
| L-C2-isseo | C2 | `에 있어서?` | `~할 때`, `~에서` |
| L-C2-double-passive | C2 | `되어지`, `보여지`, `불리워지`, `여겨지` | 홑 피동으로 |
| L-C2-one-of | C2 | `중 하나` | `특히 ~`, `~ 가운데` |
| L-C2-pronoun | C2 | 문장 첫머리 `그것은/그것이/그들은/이것은` | 대명사 생략 또는 지시 대상 명시 |
| L-C2-plural | C2 | 사전 명사 + `들` (정보·문제·기능·설정·파일·데이터·결과·항목·내용·방법·단계·화면) | 복수 표지 제거 |
| L-C2-have | C2 | `을 가지`, `를 가지`, `을 가진`, `를 가진` | `~이 있다` |
| L-C2-due-to | C2 | `로 인해`, `로 인한` | `때문에` |
| L-C3-* | C3 | 치환표 어휘 어간(수행, 존재, 확보, 소요, 요구되, 위치하, 기인, 도출) + `해당 `(명사 앞) | 치환표 참조 |
| L-C1-anthro | C1 | 무생물 주어 사전(앱·시스템·화면·버튼·트레이·설정·서버·기능·프로그램·서비스·모듈) + 조사(이/가/은/는) + (0~12자) + 금지 동사 어간(알려 주|알려주|말하|기억하|이해하|판단하|원하|기대하|도와주|챙기|품|고민하|신경 쓰|노력하) | 기계 동작 동사나 상태 서술로 |
| L-C4-opener | C4 | 문장 첫머리 `결론적으로`, `주목할 점은`, `흥미롭게도`, `종합하면`, `요컨대` | 지우고 본론으로 |
| L-C4-conj | C4 | 연속한 3문장 이상이 `또한/따라서/그리고/하지만/그러나`로 시작 | 접속사 줄이기 |

코드 블록(``` … ```), 인라인 코드(`…`), URL, 표의 코드 셀은 검사에서 뺀다(코드 식별자 보존).
줄 끝에 `<!-- ko-lint: keep <id> — 사유 -->` 주석이 있으면 그 줄의 해당 `id` finding은 `kept`로 분류해 findings에서 뺀다(§8-2 자기 수정에서 문맥상 남기기로 한 것). 반환 `stats`에 `kept: <n>`을 더한다.

### 6-3. 입출력

```
export function lintKoWriting(text: string, opts?: { docType?: 'jira'|'confluence'|'guide'|'explain'|'spec' }): {
  findings: Array<{ line: number; col: number; rule: 'C1'|'C2'|'C3'|'C4'; id: string; match: string; hint: string }>;
  stats: { lines: number; sentences: number };
}
```
CLI: `node scripts/koWritingLint.mjs <file> [--json]` — 사람이 읽는 표 또는 JSON.
`docType`의 역할:
- `guide` — C3 개발 용어 검사를 켠다(빌드·배포·인스턴스·캐시·토큰 첫 등장을 짚음).
- `spec` — §4-2 「내부 구조 문서」 행대로: EARS 키워드(`WHEN`·`WHILE`·`WHERE`·`IF`·`THEN`·`THE SYSTEM SHALL`, 볼드 포함)와 `[ai-confirmed]`·`[Event-driven]` 같은 라벨 토큰은 **같은 길이 공백으로 마스킹**해 그 뒤의 한글 서술은 검사한다. `IF-8` 같은 인터페이스 id는 마스킹하지 않는다. 줄 자체를 검사에서 빼는 것은 `- \`…\` (…) —` 꼴의 요소 목록 줄과 주석만 있는 `<!-- … -->` 줄 둘뿐이다. (설계 초안은 EARS 줄을 통째로 빼려 했으나, 계획 검증에서 실제 스펙의 finding 전부가 EARS 줄의 한글 부분에서 나와 — 그 부분이 사람이 읽는 본문이라 — 키워드 마스킹으로 바꿨다.)
- `jira`·`confluence`·`explain` — 지금은 구분 없음(전부 검사).
CLI 종료 코드: findings가 0이면 0, 있으면 1 — 게이트로 바로 쓸 수 있게.

### 6-4. 비목표
형태소 분석기 도입(외부 의존 추가), 자동 치환, 심각도 판정. 오탐은 리뷰어가 걸러낸다.

## 7. 리뷰 에이전트 — `agents/ko-writing-reviewer.md`

기존 `agents/reviewer.md` 형식(frontmatter `name`·`model`·`description`, 입력·할 일·반환)을 따른다.

### 7-1. 입력 (호출 스킬이 dispatch 시 전달)
- `text` 또는 `path`: 검사할 한글 본문(마크다운). 둘 중 하나.
- `docType`: `jira` | `confluence` | `guide` | `explain` — B1 문체 표의 어느 행을 기준으로 볼지.
- `focus`(선택): 특정 규칙만(예: `['C1','C2']`). 없으면 전부.

### 7-2. 할 일
1. `node "${CLAUDE_PLUGIN_ROOT}/scripts/koWritingLint.mjs" <path> --json` 실행 → findings 수신. `text`로 받았으면 임시 파일에 써서 넘긴다.
2. `${CLAUDE_PLUGIN_ROOT}/docs/refs/readable-writing.md`를 읽고, 본문을 **문장 단위**로 A·B·C 체크리스트에 대조한다. lint findings는 **오탐 여부만** 확정한다(문맥상 자연스러우면 버림). lint가 못 잡는 항목(C1의 사전 밖 주어, C4 리듬, B2 무주어 등)은 직접 찾는다.
3. 판정이 애매한 항목만 `${CLAUDE_PLUGIN_ROOT}/rules/vendored/yoonmoon/` 분류 원문을 읽어 근거를 잡는다. 평소에는 읽지 않는다(컨텍스트 절약).
4. 위반 문장마다 **대체 문장(after)**을 쓴다(D4). 보존 원칙(§4-3)을 지킨다. 한 문단에서 바뀌는 문장이 절반을 넘으면 그 문단의 findings는 `after` 없이 `needsHuman: true`로 표시한다(D7).
5. **원문을 수정하지 않는다.** 결과만 반환한다.

### 7-3. 반환 (verdict — 이것만 호출 스킬에 돌려준다)
```
{ verdict: 'PASS' | 'NEEDS_REPAIR',
  findings: [ { line, rule: 'A1'|…|'C4'|'PRESERVE', before, after, reason, needsHuman?: true } ],
  changeRatio: <바뀐 문장 수 / 전체 문장 수>,
  lintTotal: <lint findings 수>, lintFalsePositive: <오탐으로 버린 수> }
```
`PASS`는 findings가 0개일 때만. findings 정렬은 line 오름차순.

## 8. 소비 스킬 연결 — 계층형(D8)

### 8-1. 계층 1 — 산문: 리뷰 정확히 1회

세 스킬의 "체크리스트로 점검한다" 문장을 아래 공통 절차로 바꾼다. 문장은 각 스킬 문맥에 맞게 쓰되 절차는 같다.

```
(초안 완성 후)
1. ko-writing-reviewer를 Task로 dispatch — { path|text, docType }.
2. verdict 수신. PASS면 그대로 승인 단계로.
3. NEEDS_REPAIR면 findings의 after를 해당 문장에 그대로 끼운다(needsHuman은 건너뜀).
4. 사용자에게 before→after 표를 보인다: [행 | 규칙 | 전 | 후 | 이유]. needsHuman 항목은 별도 줄에 "확인 요망"으로.
5. 승인받는다. 재리뷰는 하지 않는다(D5).
```

- **폴백**: 서브에이전트를 못 쓰는 런타임이면 메인이 lint 실행 + 체크리스트 대조를 인라인으로 하고, "리뷰를 격리하지 못해 인라인으로 대신했다"고 한 줄 고지한다(`orchestration-policy.md` 원칙 4).
- **적용 지점**
  - `dt-worklog-sync/SKILL.md` [4] 드라이런의 "가독성 게이트" 줄 → 위 절차. `docType: 'jira'`. [2]의 "가독성 적용" 줄은 그대로 두고 C 규칙 언급만 더한다.
  - `dt-confluence-doc/SKILL.md` [4] 미리보기의 "가독성 게이트" 줄 → 위 절차. `docType: 'confluence'`.
  - `dt-explain/SKILL.md` 자가 게이트 + `references/answer-frame.md` 체크리스트 → 리뷰어 dispatch(`docType: 'explain'`) + 체크리스트에 C1~C4 네 줄 추가. dt-explain은 대화 응답이라 before→after 표는 접어서(짧게) 보이고 최종 답만 본문에 낸다.

### 8-2. 계층 2 — 내부 구조 문서: 규칙 + lint 게이트

각 author 에이전트에 세 줄을 더한다(기존 절 구조 「읽기 → 절차 → 게이트 → 핸드오프」에 맞춰):
1. **「읽기」**: `${CLAUDE_PLUGIN_ROOT}/docs/refs/readable-writing.md` — 한글 서술(페이지 목적·스토리·FR의 한글 부분·결정 근거)은 묶음 B·C를 따른다. EARS 키워드·요소 목록·라벨은 검사 대상이 아니다(§4-2 「내부 구조 문서」 행).
2. **「게이트」**: 산출 파일마다 `node "${CLAUDE_PLUGIN_ROOT}/scripts/koWritingLint.mjs" <file> --docType spec --json`을 돌려 findings를 **스스로 고친다**(대체어는 readable-writing.md 표 참조). 문맥상 자연스러워 남기는 항목은 `<!-- ko-lint: keep <id> — 사유 -->` 주석을 그 줄 끝에 붙인다(lint가 이 주석이 있는 줄의 해당 id를 건너뜀 — §6-2에 추가). 고친 뒤 재실행해 0건(또는 keep만)을 확인한다.
3. **「핸드오프」**: 반환 객체에 `writingLint: { fixed: <n>, kept: <n> }`를 더한다. 조율자는 summary에 한 줄로 보인다("한글 lint: 고침 N·유지 M").

E2E 스킬 둘은 시나리오 원장(`*.e2e-scenarios.md`, `be-journeys.md`)을 쓰는 단계에 같은 두 줄(규칙 + 저장 전 lint·자기 수정)을 더한다. Given-When-Then의 한글 서술이 대상이고, `METHOD /path`·IF-n·시나리오 id는 예외다.

LLM 리뷰어는 이 계층에 붙이지 않는다. 필요해지면 §12 후속으로.

## 12. 미결 · 후속

- C3 치환표는 시작 목록이다. 실제 리뷰에서 반복해 잡히는 낯선 말이 있으면 표에 더한다(표가 SOT — lint 사전은 표에서 생성하거나 표와 같게 유지).
- 무생물 주어 사전·금지 동사 사전도 같은 방식으로 늘린다. 두 사전은 `koWritingLint.mjs` 상단 상수로 두고, `readable-writing.md` C1 표와 어긋나지 않게 한다(테스트로 묶을지는 구현 시 판단).
- 사용자 가이드 PDF 스킬(후속 스펙)은 이 리뷰어를 `docType: 'guide'`로 쓴다. 그때 B1 사외 가이드 행의 규율이 충분한지 다시 본다.
- 계층 2에 LLM 리뷰어를 붙일지는 lint 운영 결과를 보고 정한다. `keep` 주석이 특정 id에 몰리면 그 규칙의 정규식을 좁히고, 산문 품질 불만이 lint로 안 잡히는 항목(리듬·무주어)에서 나오면 그때 spec 파이프라인에 선택 플래그(`--review-writing`)로 리뷰어를 연다.
