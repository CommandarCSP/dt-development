# 설계: 개발 정의서(Dev Definition SOT) 단계

> 열린 질문 Q1~Q5는 모두 확정됨 → [11. 확정된 결정](#11-확정된-결정). 추천값은 **(R)** 표기.

## 1. 배경 & 문제

현재 dt 파이프라인은 **UX → FE Spec(dt-spec) → FE Code(dt-implement/scaffold)** 까지만 존재한다. 두 가지 공백이 있다:

1. **FE/BE 공통 SOT 부재** — FE Spec이 API/책임 경계를 *합의가 아니라 추론·가정*으로 채운다.
   - 근거: `requirements.md` "데이터 명세 (askQuestion으로 채움)", `design.md` "검색·정렬은 서버 처리 **가정**".
2. **BE 갈래 부재** — 곧 BE Spec → BE Code gen이 추가될 예정인데, FE/BE가 공유할 기준점이 없다.

회사 워크플로우 특성상 **Figma UX를 고객사와 협의하며 기능이 바뀌는** 일이 있어, 한 번 쓰고 끝나는 문서가 아니라 변경을 흡수하는 SOT가 필요하다.

## 2. 목표 & 비목표(scope)

**목표 (In)**
- UX/요구사항 직후, FE/BE Spec 분기 **전**에 위치하는 **프로젝트 단위** 공통 SOT "개발 정의서" 도입.
- 멀티소스(Figma 페이지 순회 / PDF / 링크) 입력을 **경량 스캔**해 정의서 초안 + 사용자 협의로 확정.
- FE Spec(dt-spec) / (미래) BE Spec이 정의서를 **무조건 참조**(강제 게이트 — 정의서 없으면 페이지 생성 불가).
- 변경 추적·전파(정의서 변경 → 하위 Spec 영향 표시)의 토대 마련.

**비목표 (Out)**
- BE Spec / BE Code gen **자체 구현** — 별도 후속 작업. 본 설계는 "BE가 같은 정의서를 참조한다"는 **접점만** 둔다.
- git 전략·개발 표준(dt-frontend-*) 정의 — 각각 프로젝트 설정·FE 코드 생성 레이어 소유. 정의서는 **참조/복제하지 않음**.
- 페이지 내부 요소 scope·NFR·권한 결정 — dt-spec(페이지 스펙)이 이미 소유.
- **엔티티/도메인 모델·공통 컴포넌트 식별** — 도메인 모델은 BE 스펙, 공통 컴포넌트는 페이지 안에서 만들고 재등장 시 추출(YAGNI). 정의서가 들지 않음.
- **깊은 화면 분석**(`get_design_context` 수준 코드/스타일 추출) — dt-spec 시점으로 미룸. 정의서는 경량 스캔만.

## 3. 합의된 핵심 결정

| 결정 | 내용 |
|---|---|
| 패키징 | **새 독립 스킬 + dt-spec 게이트** (Approach 1) |
| 새 스킬 | **`dt-devspec`** — 멀티소스 경량 스캔 → 개발 정의서 생성 |
| 정의서 단위 | **프로젝트 단위 1개** (페이지 spec N개가 참조하는 SOT) |
| 정의서가 담는 것 | ① FE/BE 범위 분담 ② 인터페이스 합의(전역 규약 + 엔드포인트별) ③ 변경 추적 메타 — **3가지만(슬림)** |
| 정의서가 안 담는 것 | Phase·In/Out·NFR·권한(→ dt-spec) / 개발표준·git(→ 각 레이어·설정) / 엔티티·공통컴포넌트(→ BE스펙·페이지) |
| 입력/분석 | 멀티소스 **경량 스캔**(get_metadata + 텍스트). Figma는 화면 **전부** 받음(깊은 분석 X) |
| 성격 | 살아있는 문서 — 문서 단위=프로젝트, 변경 추적 단위=항목(SP/IF) |
| 연결 | FE/BE Spec이 정의서 **무조건 참조** (정의서 없으면 페이지 생성 불가, 플래그·예외 없음) |

## 4. 전체 아키텍처

```
멀티소스 입력 (Figma 페이지 순회 / PDF / 링크)
        │  경량 스캔: get_metadata(프레임 전체) + 텍스트 추출  (깊은 코드 분석 X)
        ▼
┌──────────────────────────────────────┐
│  dt-devspec  (신규 스킬)               │
│   1. 멀티소스 경량 수집·스캔            │
│   2. FE/BE 경계·인터페이스 후보 추론     │
│   3. askQuestion으로 협의·확정          │
│   4. 개발 정의서 산출/갱신 (SOT)        │
└──────────────────────────────────────┘
        ▼
  docs/specs/definition.md          ← 프로젝트 개발 정의서 (SOT · 1개 · 상위)
        │  ▲──── 무조건 참조 (강제 게이트 — 정의서 필수) ────┐
        ├─→ docs/specs/pages/<page>/  FE Spec (dt-spec) ──┤   ← 페이지마다 N개 (하위)
        └─→ BE Spec (미래) ───────────────────────────────┘
              ▼                      ▼
           FE Code                BE Code
        (dt-frontend-* 표준)     (BE 표준, 미래)
```

`definition.md`(specs 루트)가 `pages/`의 **부모 위치** → "상위 정의서 / 하위 spec" 구조를 디렉터리로도 만족. 'pages' 세그먼트 불일치 문제 없음.

## 5. 신규 스킬: `dt-devspec`

### 입력
- 멀티소스: Figma 페이지 URL(들) / PDF / 웹 링크 / Markdown.
- 기존 `docs/project-context.md`(있으면) — 도메인 용어·제약 참조.

### 처리 단계
1. **경량 수집·스캔** — Figma는 *페이지 ID → `get_metadata`로 프레임 전체 순회 → 프레임 인벤토리 + 텍스트 추출*. **깊은 `get_design_context`는 호출하지 않는다**(코드/스타일은 정의서에 불필요). 문서 소스는 텍스트 파싱.
   - Figma 화면은 **전부** 받는다(범위 자르지 않음). 입력이 너무 무거우면 사용자가 소스를 문서로 바꿔 조절.
2. **FE/BE 경계 추론** — 각 기능·책임을 `FE | BE | 공통` 후보로 분류(신뢰도 `confident | ambiguous`).
3. **협의·확정** — ambiguous 항목·인터페이스 합의를 사용자에게 질문(`ask-missing` 패턴 차용).
4. **정의서 산출/갱신** — 아래 스키마로 작성. 재실행 시 **diff-then-confirm**(자동 덮어쓰기 금지). 프로젝트 정의서 1개에 항목을 **누적·갱신**한다.

### 산출물 — 위치/형식
- 위치: **`docs/specs/definition.md`** (프로젝트당 1개, specs 루트 = pages/ 의 부모).
- 형식: Markdown + 메타 헤더(기존 dt-spec 산출물과 **동일 4줄 컨벤션** + definitionVersion 1줄).

## 6. 개발 정의서 산출물 스키마

```markdown
<!-- Generated by dt-devspec@<ver> at <ISO time> -->
<!-- status: draft -->
<!-- sources: figma:... , doc:... -->
<!-- specVersion: 1.1 -->
<!-- definitionVersion: 1 -->          ← 변경 추적용. 단조 증가 "베어 정수"(v1/1.0 금지; 8절 버전 비교 전제)

# 개발 정의서: <project>

## 전역 규약 (Global Conventions)   — 프로젝트 1회, 모든 IF가 상속
- 에러 응답 포맷 / 에러코드 체계
- ID 타입 (number | string/UUID)
- 날짜·타임존 표기
- 페이지네이션 방식 (offset | cursor)
- 인증 방식
- 멱등성 정책
(handoff-checklist의 cross-cutting 항목을 여기 1곳에 모은다 = 페이지별 중복 제거)

## 범위 분담 (Scope Split)            — 페이지·기능을 가로질러
| ID    | 기능/책임             | 담당   | 신뢰도     | 비고(분담 근거 한 줄만) |
|-------|----------------------|--------|-----------|------------------------|
| SP-1  | 파일 목록 조회·검색·정렬 | BE+FE | confident | 검색·정렬은 서버 |
| SP-2  | 선택 집합(체크박스)      | FE    | confident | 화면 로컬 상태라 FE |
| SP-3  | 비동기 압축 다운로드      | BE    | confident | 압축·메일 발송이 서버 |

## 인터페이스 합의 (Interface Contract) — 엔드포인트별(전역 규약 상속)
| ID   | 엔드포인트 | 메서드 | 요청 | 응답 | 합의 상태 |
|------|-----------|--------|------|------|----------|
| IF-1 | /api/files | GET | q,sortField,sortOrder | { items: File[] } | agreed |
| IF-2 | /api/files | POST | multipart(file,content) | 201 {id,...} | agreed |

## 변경 추적 (Traceability)
- 각 SP/IF 항목 ID는 안정적 키. FE/BE Spec이 이 ID를 역참조한다.
```

> **비고 칸 규칙(슬림 유지)**: 비고는 **"FE/BE 분담 판단 근거 한 줄"만**. 구현 상세(상태 관리 방식·압축 알고리즘·메일 절차 등)는 dt-spec 소유라 적지 않는다. (허용 "검색·정렬은 서버" / 금지 "useReducer로 선택 관리".)

각 항목의 **안정적 ID**(SP-n / IF-n)가 변경 전파의 핵심 장치다.

## 7. dt-spec 게이트 (수정사항)

프로젝트 단위라 게이트는 단순하다 — **프로젝트 정의서 1개**만 보면 된다. **정의서가 없으면 페이지 생성(dt-spec)을 무조건 막는다** (플래그·예외·마이그레이션 유예 없음).

- dt-spec(및 미래 BE Spec) 실행 **시작 시**:
  1. `docs/specs/definition.md` 존재·유효성 확인. **없으면 중단** → *"먼저 `dt-devspec`을 실행해 개발 정의서를 만드세요."*
  2. 정의서의 `definitionVersion`(베어 정수)을 읽어 spec 헤더에 기록(`<!-- basedOnDefinition: 1 -->`).
- dt-spec은 정의서의 **자기 담당(FE/공통) 항목만** 스펙화. BE 전용 항목은 스킵(BE Spec 몫).
- 기존 데이터 명세를 *추론*하던 부분 → 정의서 IF-n을 **확정값으로 인용**.
- **역참조 emit(전파 입력 생성)**: 정의서 항목을 스펙화할 때 해당 FR/IF에 `<!-- from: SP-n -->`/`<!-- from: IF-n -->`를 써넣는다. 이것이 8절 step4 전파의 입력이며, 없으면 전파가 작동하지 않는다.

## 8. 변경 추적 & 전파

1. Figma/문서 변경 → `dt-devspec` 재실행 → **diff-then-confirm**으로 바뀐 SP/IF 항목 식별 + `definitionVersion` 증가.
2. 바뀐 항목 ID 목록 산출.
3. FE/BE Spec 재실행/점검 시, spec 헤더 `basedOnDefinition`(정수) vs 현재 `definitionVersion`(정수) **단조 증가 정수 비교** → 후자가 크면 **"영향받는 FR/IF 재검토 필요"** 경고.
4. **영향 항목 정밀 산출** — spec 내 `<!-- from: IF-n -->` 역참조(7절 emit)를 역추적해 어떤 FR/IF가 영향받는지 계산. step3의 "영향 항목 나열"은 이 결과다.

> **MVP 경계**: (3) 버전 경고 + (4) 역참조 기반 영향 항목 산출까지 포함. 영향 항목을 받아 spec을 **자동 재작성**하는 것만 비범위.

## 9. dt-spec 컴포넌트: 재사용 vs 재구현

분석은 **재사용하지 않는다** — dt-spec의 깊은 분석(`get_design_context` 기반)은 화면 1개를 코드 수준으로 파는 것이라 프로젝트 조망용 정의서에 부적합(토큰 폭발). 정의서는 **경량 스캔을 자체 수행**한다.

| dt-spec 컴포넌트 | 구분 | 비고 |
|---|---|---|
| 화면 깊은 분석 (`analyze-figma` 등 get_design_context 경로) | **재사용 안 함** | 정의서는 `get_metadata`+텍스트 경량 스캔을 **자체 수행**. 깊은 분석은 dt-spec 시점으로 미룸 |
| 입력층 (URL 파싱·소스 식별·Figma 페어링) | **실행 재사용** 가능 | 경량 공통 유틸 수준 |
| `ask-missing` | **패턴 차용**(신규 구현) | 질문 흐름만 동형, FE/BE 경계·인터페이스 합의용 |
| `diff-then-confirm` | **패턴 차용**(신규 구현) | 재실행 비교만 동형, SP/IF diff용 |
| 메타 헤더 컨벤션 | **컨벤션 차용** | 동일 4줄 표기 + definitionVersion |

→ "중복 구현 없음" 같은 과장 단언을 하지 않는다. 분석은 경량 신규, 나머지는 패턴/컨벤션 차용이 정확한 그림이다.

## 10. 테스트/검증 전략

- 정의서 스키마 유효성: 필수 섹션(전역 규약/범위 분담/인터페이스/추적)·ID 형식·헤더 5줄·definitionVersion 정수 체크.
- 게이트 동작: 플래그 on + 정의서 없음 → 중단 / 플래그 off → 기존 동작 / 버전 불일치 → 경고.
- diff-then-confirm 회귀: 같은 입력 재실행 no-op, 일부 변경 시 해당 ID만 diff.
- **변경 전파 검증**(핵심): IF-2 변경 + `definitionVersion` 증가 → 버전 비교가 불일치를 잡고 `<!-- from: IF-2 -->`를 가진 spec 항목**만** 영향 목록에 표시(다른 항목 미표시).
- 경량 스캔 검증: 다수 프레임 페이지 입력 시 `get_design_context`가 호출되지 않음(깊은 분석 회피) 확인.
- 기존 dt-development 플러그인 테스트 관례(`plugin/tests`) 따름.
